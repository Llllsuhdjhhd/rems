# REMS 递归演化记忆系统规范（完整工程版）

本文是在原始核心规范基础上，融合了面向生产环境的动态信念修正、情感遗忘模型、上下文防溢出策略、多场景输出适配、记忆重组机制，以及基于提示词注入的全局代词消解引擎与动态粒度路由的完整工程化技术白皮书。

## 1. 基本事件定义

基本事件（Basic Event）是 REMS 中承载客观事实的最小记忆单元。基于最新的架构逻辑，基本事件不仅记录事实片段，还承载角色在当次事件中的瞬时状态（快照与情感），确保事件的可验证性与主体交互的完整性。

### 1.1 核心属性解析

#### 1.1.1 唯一标识与元数据

- `event_id`：废除传统的字典序生成方式，全面引入**无状态的唯一标识**。系统改用无状态的分布式 ID 生成算法（如 UUID v7、Snowflake 等），消除节点依赖，确保系统内所有事件在分布式环境下的唯一性、可区分性与完全无状态。
- `create_time`：记录事件封装完成的绝对时刻。

#### 1.1.2 原始数据属性

原始数据是基本事件的唯一数据底库，作为记忆系统生成、演化与追溯的绝对事实基准。

- `content_raw`：即 L0级原始文本。
  - 基本事件：交叉事件被剥离（Disentanglement）后，抽取出的专属于该事件主线的最纯粹原始文本片段（去除无干扰和其他事件线内容）。
  - 抽象事件：由其叶子基本事件的 `content_raw` 拼接为证据后，按基本事件同样的“抓住重点、保留主干”规则压缩生成；目标长度约等于这些基本事件 `content_raw` 的平均长度。若 `source_events` 中包含已有抽象事件，系统先展开到叶子基本事件再取其 `content_raw`，避免基于上一轮抽象文本继续抽象。

#### 1.1.3 递归摘要体系属性 (Recursive Summary Hierarchy)

系统通过同步生成的 L1~L10 摘要来实现记忆的物理压缩与语义浓缩的动态平衡。

- `summaries`：以字典形式存储各级摘要。遵循 **指数级衰减原则 (λ=0.5)**。
  - **层级预算分配**：L1 为最高保真压缩（默认上限 127 字），后续层级 $L_n$ 的字数预算遵循 $Budget_n = Budget_{n-1} \times 0.5$ 的递归衰减。
  - **动态熔断 (Summary Fuse)**：系统执行实时语义熵检测。一旦某级摘要的生成长度 **不高于 20 字符（≤ 20）**，则判定该事件在此细节深度下已达到信息表达极限，系统将立即触发熔断，停止生成后续更高级别的摘要（Summaries 字典将不再包含更高键值）。阈值可配置（`summary_fuse_min_chars`，默认 20）。
- `summary_lengths`：记录各级摘要的实际字符数，用于代谢评分。
- `actual_max_level`：记录触发熔断前的实际最高层级。

#### 1.1.4 角色交互与瞬时状态属性

通过 `role_list` 记录当次事件中所有参与者的交互细节及量化快照。

- `role_list`
  - `role_id`：关联至角色系统的唯一 ID。
  - `importance`：`S/A/B/C/D` 五级分级。
  - `role_snapshot`：角色在当次事件中的瞬时分级切片，遵循 **指数级递减模型 (λ=0.4)**：
    - **L3 (详细意图)**：全量保留角色的微观动作、心理意图及环境交互细节。仅核心主角（S级）拥有此层级。作为信息的源头，其字数受当前事件 `raw_len` 的最高权重限制。
    - **L2 (互动逻辑)**：字数预算约为 L3 的 **40%**。侧重于记录该角色与其他实体的互动反馈与行为逻辑。
    - **L1 (骨架白描)**：字数预算约为 L2 的 **40%**。极致简练。配角（A-D级）强制降级至此级。
  - `emotional_model`：记录角色的情感量化状态与波动参数（详细计算逻辑见 2.5 节独立情感与认知调节模块）。
- **抽象事件特例**：抽象事件的 `role_list` **恒为空**，不登记 `role_snapshot`、不登记 `emotional_model`，也不触发任何角色白描追加或语义卡片刷新。但抽象合成的输入必须携带基本事件中的角色线索，压缩 `content_raw` 时不能漏掉关键角色/实体；角色只作为事实主干的一部分被提炼进文本，不作为结构化角色对象登记（详见 §3.1）。

#### 1.1.5 抽象演化与生命周期标记

- `is_abstract`：架构级常量。基本事件固定为 `False`，抽象事件固定为 `True`。
- `is_abstracted`：演化状态位，记录该基本事件是否已被某条抽象事件纳入 `source_events`（即已作为子集的一员参与抽象合成）。
- `status`：反映事件在回忆系统中的权重（未闭环 / 活跃 / 静默）。

#### 1.1.6 扩展属性与规律内核

- `decoration`：针对 `content_raw` 的非事实性描述，支撑“梦见”系统。
- `insight`：基本事件固定为 `None`；抽象事件的 insight 由开关 `enable_abstract_insight` 控制，默认关闭。开启时仅存储跨事件提炼出的规律/认知结论，不作为事实本身的摘要；关闭时抽象事件只保留 `content_raw` 与递归摘要。

#### 1.1.7 事件聚合与长度约束属性

- `event_length`：记录 L0 级原始文本的字符长度。
- **物理防御约束**：最高上限设定为 `1/66 * Context_Window`。
- **工程化语义聚合（防碎片化机制）**：对于极其琐碎的短小动作，系统需具备上下文聚合能力，将细粒度连贯动作归于同一个事件中。
  - **判定案例**：当输入为*“我去跑了步，然后就回家了。回家后我打扫了卫生，大概1小时后，看了一会儿小说”*。系统不应将其拆分为四个极短的微小事件，而应在缓冲区聚合封装为单一基本事件：`"content_raw": "用户去跑步后回家，依次打扫了卫生并阅读了一小时小说。"`

#### 1.1.8 抽象事件专用扩展属性

- `abstraction_level`：记录该事件在递归演化树中的深度（首层抽象 = 1；以抽象事件为成员再次被纳入更高阶抽象时递增）。
- `source_events`：存储触发本次抽象合成的**频繁极大子集**中的全部事件 ID 列表。该列表的元素可以是基本事件 ID，也可以是已有的抽象事件 ID——抽象事件生成后会以其自身 ID 替换 `recall_log` 中的原子集，使更高阶抽象在同一命名空间继续演进（详见 §3.2 触发机制）。
- **抽象链反查基本事件**：出于审计、向量检索结果溯源或对话生成时"从规律回到事实"的需要，仓储层提供 `EventRepository.resolve_basic_event_ids(event_id)`：对 `source_events` 做 BFS 递归展开（每遇抽象事件就继续下钻），返回该抽象事件传递依赖的全部**叶子基本事件** ID 去重列表；若传入的本就是基本事件，则原样返回。因此从任意抽象事件都能在一次调用内拿到其全部事实支撑。
- **字段缺省**：抽象事件不登记 `role_list`（恒为空）、不登记 `role_snapshot` / `emotional_model`；其 `summaries`（L1…Ln）由 §1.1.3 递归摘要体系基于 `content_raw` 正常生成，与基本事件同规则。

## 1.2 动态压缩率控制（Dynamic Compression Ratio Control）

为了在有限的上下文窗口预算下精确控制每个事件的「信息膨胀度」，系统引入动态压缩率机制，确保事件代谢所产生的全部衍生数据与原始文本之间维持可控、可预测的比例关系。

### 1.2.1 压缩率定义

- **原始数据长度 `raw_len`**：事件的 `content_raw`（L0 级原始文本）字符长度。
- **衍生数据总长 `sum_len`**：事件封存后产生的全部衍生数据字符数之和，具体包括：
  1. **默认级摘要**：`summaries` 中取中位层级（`mid_summary_key` 对应的级别，如 L2）的文本长度。仅核算系统默认使用的该级别，而非所有摘要级别的总和。
  2. **角色快照（默认级）**：`role_list` 中每个角色的 `role_snapshot` 在默认级别（如 `l2_interaction` 互动白描）的文本长度之和。
  3. **角色白描条目**：写入角色白描时间线的 `WhitePaintingEntry.role_summary` 的文本长度之和（即本次事件向各角色时间线贡献的内容）。
  4. **装饰 `decoration`**：非事实性描述的文本长度。
- **压缩率 `compression_ratio`**：定义为 `sum_len / raw_len`。

### 1.2.2 目标压缩率与动态前置预算

- **目标压缩率（`compression_target_ratio`）**：系统默认维持 `1/6.6`（约 0.1515）。
- **短文本宽恕机制（平滑补偿）**：为防止短文本因严格执行压缩率而导致信息丢失，预计算时引入动态补偿：
  - `effective_ratio = target_ratio + (1.0 - target_ratio) * exp(-raw_len / 500)`
  - 当 `raw_len` 较小时，压缩率自动放宽，允许保留更多细节；当文本较长时，压缩率收敛于 `1/6.6`。
- **前置预算计算**：在封存流程最前端确定衍生数据总预算：
  1. **总预算**：`total_budget = raw_len × effective_ratio × compression_budget_multiplier`。
  2. **提示词注入**：预算以硬约束形式注入提示词（如“请将 L1 摘要控制在 XX 字以内”）。
- **缩放因子（`compression_budget_multiplier`）**：默认值为 1.0。用于全局手动微调。
- **工程化说明**：预算分项比例不要求每个事件精确遵循，而是作为 LLM 的「建议上限」。当角色数量极少（如仅 1 个角色）时，快照与白描预算可合并使用；当角色数量极多时，单个角色的预算自然收窄以维持总量守恒。

## 2. 角色系统定义与动态遗忘机制

角色系统（Role System）的核心职能是维护全局唯一的角色标识（`role_id`），并将分散在不同基本事件中的事实按时间顺序收集，形成角色的状态机。

### 2.1 角色标识与独立性与“可疑属性”机制

- 角色 ID（`role_id`）是持久化的“容器指针”，用于归集实体行为记录。
- 去代词化映射：强制要求在输入转化为基本事件时，通过 `role_id` 替换模糊代词。
- **历史角色身份仲裁（Entity Resolution）**：回忆块（Recall Block）调出的历史角色如果在语义上与当前新出现的角色存在一致性连结，系统必须执行仲裁确认以判定其是否为同一实体。若判定为同一个角色，系统必须强制复用已有的历史 `role_id`，坚决防止同一个逻辑角色在系统中分裂产生多个截然不同的 ID 副本。
- **角色新增“可疑（Suspicious）”属性**：为应对充满噪声与歧义的文本，角色层级新增“可疑”状态标识。系统仅在以下两条异常途径下将角色标记为“可疑”对象，以备后续修正：
  1. **长度溢界导致强制封装**：当模糊输入长度大幅超界（＞ `msg_len * 1.2`）且必须强制生成事件时，由于无法判断核心身份，系统只能生成临时的对象替代，此时将被打上可疑标记。
  2. **仲裁边界不定**：当系统执行新老指代身份仲裁时难以确信，既不能肯定、也不能轻易否决时，系统将其标记为可疑角色。

### 2.2 全局模式切换与提示词注入引擎（代词消解）

在实际工程落地中，试图在底层代码中穷举所有可能的业务场景缺乏可行性。针对多变语境下的代词（如“我”、“他”）消解问题，系统通过在初始化阶段提供**“单人模式（Single-User）”**或**“多人模式（Multi-User）”**的系统级配置，将环境上下文作为额外信息动态注入到大模型的系统提示词（System Prompt）中，在角色界定与提取时直接指导模型的推理行为。

- **单人模式（Single-user Mode）**
  - **适用边界**：个人备忘录、单主角语音记录、私密生活日志等单一主体的交互环境。
  - **提示词注入策略**：系统后台在封装事件的提示词中明确附加约束条件：“当前系统运行于单人隔离模式。上下文中所有第一人称代词（‘我’、‘我的’）以及缺乏明确主语的动作，均极大可能指向唯一核心用户实体 ``。”
  - **工程优势**：通过模型提示词的硬性约束，极大降低大模型在代词推断上的算力开销与幻觉可能，保障个人上下文的高度一致性。
- **多人模式（Multi-user Mode）**
  - **适用边界**：群组互动、多人会议录音、复杂多 NPC 游戏沙盒等并发环境。
  - **提示词注入策略**：系统在提示词中额外提供环境花名册与消解指令：“当前为多实体交互场景，已知活跃参与者包含 ``。请务必结合对话历史、时间戳与发言者账号/声纹标签，执行精确的多方代词消解（Multiparty Coreference Resolution）。严禁将模糊代词默认归属于单一核心用户。”
  - **工程优势**：将角色排查的任务通过精细化 Prompt 下放给大模型自身的逻辑推理能力，同时为其提供可供比对的实体清单，既保持了架构的简洁，又适应了多线程并行对话的需求。

### 2.3 角色白描系统与代谢遗忘 (Chronological White-painting & Metabolic Forgetting)

- **收集与汇编（动态粒度路由）**：系统在将基本事件中的记录汇编到角色白描轴（时间线）时，基于角色权重与运行模式执行**极度克制**的详细程度分配：
  - **常规角色（配角强制降级）**：绝大多数配角（S 级以下）仅拥有 L1（极简白描 / 动作骨架）被提取并追加至时间线。这在维持配角状态机连贯性的同时，以最激进的方式控制了写入体积。
  - **主角/核心角色（详细提取）**：只有处于“单人模式”的核心用户，或在多人模式下被明确标定为 S 级地位的绝对主角，系统才允许并强制拉取 L1~L3（详细白描与决策级）。
- **动态遗忘因子 (Dynamic Forgetting Factor)**：
  - 每个白描条目（WhitePaintingEntry）均持有 `forgetting_factor`、`base_forgetting_factor` 以及 `last_accessed_time`。
  - **初始权重**：取决于事件的感官能量（AE）。对于极具冲击力的事件，`base_forgetting_factor` 可初始化至极高值（如 100.0），确保其“终身难忘”。
  - **指数衰减**：在回忆检索阶段，系统根据 $t - last\_accessed\_time$ 动态计算衰减后的有效权重。
  - **静默阈值 (Silencing)**：当有效遗忘因子衰减至 **0.02** 以下时，该记忆条目进入“静默状态（SILENT）”，在向量检索中将被物理性忽略（Where 过滤），实现生物级遗忘。
  - **回忆加强 (Memory Recovery)**：一旦记忆在回忆块中成功出现，其 `forgetting_factor` 将获得 1.5 倍的增益恢复（不超过 base 值），并刷新 `last_accessed_time`。
- **容量外：软遗忘启动**：当白描总长突破容量上限后，系统开始对最早条目施加额外的衰减惩罚。
- **物理保留原则**：无论遗忘因子如何衰减，白描条目在数据库中永远不被物理删除，遗忘仅影响「检索可见性」。

### 2.4 双轨制认知状态机与语义卡片

- 为彻底根治线性白描带来的检索稀释，系统建立双轨制：在时间线白描外，维护“高密度语义状态卡片”。
- 该卡片存储极致压缩的键值对。
  - **状态卡片案例**：系统将成百上千条白描流水在后台压缩为卡片词典：`{"Role_ID": "ROL-001", "核心偏好": ["深烘焙咖啡", "抗拒酸味"], "性格均值": {"易激惹度": 0.2}}`。在交互中，系统优先拉取该卡片提供绝对基准。
- **刷新策略（工程化）**：
  - 卡片的 **LLM 合并刷新** 仅对「主要角色」（重要性 `S`/`A`，或单人模式下的核心用户）触发；次要角色（B/C/D）跳过 LLM 调用，只在白描时间线层累积。
  - 系统提供开关 `enable_insight`（默认 **关闭**）以进一步抑制 LLM 合并开销；关闭时白描时间线仍正常写入，检索阶段退回到时间线白描聚合，不影响记忆正确性。
- **与抽象事件的关系**：抽象事件 **不登记角色**，因此对语义卡片维护无贡献；卡片的数据来源**仅**为基本事件封存后的白描追加流程。

### 2.5 独立情感与认知调节模块（Independent Emotion & Cognitive Modulation Module）

为了科学、可控地计算事件对角色情感的影响，系统剥离了单凭大模型“随意感知”的逻辑，专门设立了基于学术界通用计算标准的独立情感模块。该模块将佛教心理学（五受 Vedana 与六根本烦恼 Klesha）的量化需求，深度挂载到以下两个计算情感引擎中：

- **基于 OCC 模型的基准评估 (Appraisal Framework)**：系统底层采用认知科学中广泛成熟的 **OCC 模型**（Ortony, Collins & Clore）。该模型通过一套确定性的规则，评估当前事件、代理行为和对象对角色内在目标和偏好的影响（Self-appraisal），从而计算出科学、标准化的情感触发基准，防止情感赋予的随意性 ``。
- **基于 EMA 模型的动态演化 (Dynamic Evolution)**：引入 **EMA（情绪与适应，EMotion and Adaptation）模型** 机制。该机制专门用于模拟情感状态（如“嗔”或“苦”）随时间的动态演变。情感量化不仅是静态打分，它会持续评估目标进度与现实预期的差异，并直接干预角色的适应性行为与后续决策 `[1]`。
- **常态默认情感值与记忆存留基准**：情感系统是记忆保留机制的最底层骨架。系统内所有情绪维度的**初始默认值均统一设定为 1.0**。对于极为普通的日常活动（如普通的吃饭、喝水散步等），模型仅赋予 1.0 的平坦情感默认值；此类缺乏情感波峰的琐碎事件仅在短时窗口内可被提取（即短期记得），而在长周期的历史演化中将会被极快速触发衰退并彻底遗忘。
- **与记忆初始值的硬绑定机制**：基于 OCC 与 EMA 双模型的联合计算输出，当某事件引发剧烈的情感波峰（例如极高唤醒度的“极乐”或“大苦”，引发大量偏离 1.0 基础值的溢出参数）时，系统架构将直接把该绝对差映射为极高的“记忆初始值”与“激活能量”。重大情感事件天然获得最强的抗遗忘权重，这为智能体提供了极其真实、不可篡改的心理创伤或高光记忆机制。

## 3. 抽象事件定义与防幻觉规范

抽象事件（Abstract Event）通过对多次回忆中**反复共现**的低阶事件子集做归纳，形成具备跨时间属性的高阶认知节点。

### 3.1 核心属性解析

结构与基本事件一致，但存在以下硬性差异：

- `content_raw`：大模型基于 `source_events` 展开得到的叶子基本事件 `content_raw` 拼接输入，按基本事件同样的“抓住重点”规则压缩生成；目标长度约等于叶子基本事件 `content_raw` 的均值；
- `summaries`：按 §1.1.3 递归摘要体系 **基于 `content_raw` 正常生成**（L1…Ln + ≤ 20 字符熔断），与基本事件同规则；
- `insight`：由 `enable_abstract_insight` 开关控制。开启时生成跨事件提炼出的规律/认知结论，不复述事实本身；关闭时不生成；
- `is_abstract`：固定为 `True`；
- `role_list` **恒为空**；抽象事件 **不登记角色、不生成角色快照、不生成情感量化、不触发任何角色白描追加或语义卡片刷新**。但合成输入必须带入基本事件的角色线索，压缩 `content_raw` 时不能漏掉关键角色/实体；
- `abstraction_level`：记录在递归演化树中的深度，支持抽象事件再作为其他抽象事件的子集成员参与更高阶合成。

### 3.2 抽象事件的触发机制（唯一路径：频繁极大子集挖掘）

抽象事件的合成 **不再** 依赖任何向量近邻聚类或定期扫描。其 **唯一触发路径** 为：**回忆块事件集合中的频繁极大子集挖掘**。

- **登记阶段**：每次 ``RecallService.build_recall_block`` 成功产出回忆块后，将块内所有 *真实事件 ID*（即 basic 与 abstract，过滤 `CARD:*` 等伪条目）的有序去重集合，作为一条记录写入 `recall_log` 表。
- **挖掘阶段**：对 `recall_log` 的历史记录族 $\{T_1, T_2, \dots\}$（每个 $T_i$ 为一次回忆的事件 ID 集合），寻找**极大频繁子集** $S$ 满足：
  1. `|S| ≥ abstract_subset_min_size`（默认 **6**，可配置，硬门槛防止两三个事件就合成抽象，稀释语义）；
  2. 存在 $\mathrm{support}(S) = |\{T_i : S \subseteq T_i\}| \ge$ `abstract_subset_min_support`（默认 **5**，"≥5"，可配置）；
  3. 不存在另一个频繁子集 $S'$ 同时满足 $S \subsetneq S'$（即 $S$ 在频繁集合族内 **极大**，避免同构的小子集重复合成抽象）。
- **合成阶段**：对每个通过阈值的 $S$，以其成员作为 `source_events`；调用归纳演化技能（`InductiveEvolutionSkill`）时先将成员递归展开到叶子基本事件，拼接这些基本事件的 `content_raw` 与角色线索作为输入，合成压缩后的抽象事件 `content_raw`；持久化后调用 §1.1.3 的 `SummaryGenerationSkill` 为其 `content_raw` 生成多级摘要与 `actual_max_level`，再索引入向量库。
- **幂等 & 同名空间迭代（抽象事件可再次抽象）**：
  1. 每条抽象事件生成后会把其指纹（$S$ 成员排序后拼接）登记到 `abstracted_subsets` 表，同一 $S$ 不会被重复合成；
  2. 生成后会遍历所有满足 $S \subseteq T_i$ 的历史 `recall_log` 行，将其中的 $S$ 成员移除，插入新抽象事件 ID。"**用抽象事件 ID 代替原来的子集**"使得挖掘逻辑在**单一命名空间**内统一：后续回忆块若仍然整体命中该抽象事件，会与历史记录在同一空间里累积支持度；若多个已合成的抽象事件再度频繁共现，即触发 **更高阶抽象**（$source\_events$ 可直接嵌套抽象事件 ID，$abstraction\_level$ 递增），自然形成多阶演化树；
  3. `source_events` 内的基本事件会被标记 `is_abstracted = True`（仅基本事件；嵌套的抽象事件不做此标记，因为它们本身也是高阶演化的中间节点）；
  4. **从抽象反查基本事件**：需要溯源到事实层时，调用 `EventRepository.resolve_basic_event_ids(event_id)` 即可沿整条 `source_events` 链路 BFS 展开到叶子基本事件，无论抽象有多少层（见 §1.1.8）。这使得"规律 → 事实"的检索在任意阶抽象上都保持 O(1) API。
- **举例（直观说明）**：若两次回忆块分别为 `(22, 55, 33, 88, 79, 66, 12)` 与 `(22, 33, 88, 79, 66, 111, 2212)`，其交集 `{22, 33, 88, 79, 66}` 作为候选被跟踪；再出现 3 次（总支持度 ≥ 5）且大小达到 `abstract_subset_min_size` 时即触发合成。若同时存在更大的频繁子集 $S' \supset S$，则只保留极大的 $S'$ 生成一条抽象事件。

挖掘既可在每次 `ingest` 末尾增量执行（`AbstractionService.mine_and_synthesize`），也可由外部批处理任务调用（参见 `REMSPipeline.run_evolution`）。

### 3.3 幻觉控制与防强化循环

- **危险的自我强化循环规避**：如果系统仅用于后台记录（无需通过记忆进行预测或对话输出），则不存在该问题。
- 若应用于多轮交互场景，为了防止抽象推演结论被反复当作原始事实入库造成幻觉闭环，归纳演化技能在合成时**始终**展开到叶子基本事件，并以基本事件 **`content_raw`**（而非中间级摘要或上一轮抽象文本）作为证据输入。抽象事件参与更高阶合成时同样先反查到基本事实层。

## 4. 事件代谢素材、触发机制与回忆提取规范

### 4.1 残影（Shadow）与未完成事件的精准剥离

- **残影**：存留在系统缓冲区内、未经整理的原始文本素材。
- **未完成事件库**：存储已开启但未闭环的逻辑对象。
- **复杂输入的精准剥离案例**：
  - 当系统接收到输入：*“我去跑了步，然后就回家了。回家后我打扫了卫生，然后继续进行A项目的研发，大概1小时后，看了一会儿小说”*。
  - 判定与剥离逻辑：大模型扫描到“A项目的研发”时，通过检索命中未完成事件库中的历史挂起事件（例如几天前开启的 A 项目逻辑实体）。此时，系统必须精准划开边界：将“打扫卫生”与“看小说”剥离出来作为全新的基本事件封装；将“继续研发A项目 1小时”单独抽离，归入库中已存在的 A 项目未完成事件，更新其完成进度与状态。这种分离机制保证了宏观长期任务与微观即时琐事的物理隔离。

### 4.2 事件剥离与序号编码协议 (Event Disentanglement & ID Encoding)

为了最大限度优化模型在代谢过程中的 Token 消耗，系统废弃了传统的“全文本提取”模式，全面采用 **Sentence-ID Encoding（序号编码）协议**。

- **分句索引化**：系统将一段充满冗余、交叉的残影（Shadow）文本预先进行语义分句，并标记为 `[序号] 文本` 格式。
- **零文本返回 (Zero-Text Exchange)**：在剥离事件（Disentanglement）时，大模型不再从 JSON 中返回 `content_raw` 字符串，而是通过返回对应的句序列表 `content_raw_indices`（例如 `[1, 2, 5]`）来界定范围。**禁止返回原文 text**。
- **物理还原逻辑**：系统在接收到模型返回的索引序列后，在本地（EventService）直接根据索引碎片还原出完整的 `content_raw`。
- **工程优势**：
  - **极致吞吐量**：通过消除大规模原文在模型上下文中的冗余双向传输，显著提升大模型的处理吞吐量，并大幅降低 Token 补全成本。
  - **边界完整性**：确保每个事件的原始文本严丝合缝地来源于输入源，消除了模型在物理搬运原文时可能产生的幻觉（漏删、错字）。
- **事件剥离与合并摘要 (Disentanglement & Summarization)**：架构层面允许「剥离 + 摘要 + 角色」在一次 LLM 调用中完成。本参考实现出于 prompt 噪声控制与角色抽取稳定性考虑，将其**拆分为两步**：
  1. `BoundaryDetectionSkill`：只做序号剥离、残影与未完成事件判定，**不输出**摘要或角色；
  2. `EventEnrichmentSkill`：基于剥离出的 `content_raw` 在**同一次**调用内同时产出 L1…Ln 多级摘要（按 §1.1.3 熔断）与角色列表 / 快照 / 情感量化（按 §1.1.4 分级）。
  两步组合在代谢总调用次数上与单次等价（每事件 1 次 enrichment），但实测显著改善了角色抽取在长摘要指令下的覆盖率。
- **增强型生成前置条件机制**：在判定客观片段是否能够封装为正式事件时，除依赖语义闭环外，必须额外满足以下两个硬性约束条件以拦截无意义碎片入库：
  1. **输入长度底线**：积累的源输入文本长度必须大于 `msg_len / 6.6`，方可考虑作为一个具备宏观记录价值的事件单元落地入库。
  2. **核心角色确定性保障**：对于事件中涉及的主要参与角色，系统必须基本确定其现实身份定位（能够挂载固定的 `role_id` 及清晰的实体面貌）。如果面对模糊或含混的输入，使得系统确认不了核心对象是谁，则尝试悬置为未决片段在缓冲区挂起，不急于生成事件。**底线兜底触发**：若该模糊信息的积累长度已经越过红线界限（逾越 `msg_len` 的 1.2 倍），为防止内存与计算爆炸，系统不再等待，**强制立刻剥离并生成事件**。是否为该事件附带「可疑（Suspicious）」角色占位 **由下游角色抽取与 `RoleService` 仲裁决定**（当 `EventEnrichmentSkill` 无法产出合规角色或仲裁判定主体身份不确定时，注册 `is_suspicious=True` 的临时占位角色），而不在长度阈值触发点硬性置位——避免把「物理长度越线」误等同于「身份不明」。
- **中间模糊截断机制**：由于现实中信息往往是无头无尾的，大模型从长文本中只能剥离出上半部分的完整事实，剩下的未闭环残留部分则继续作为“残影（Shadow）”在此截断并滞留。截断部分入库，剩余部分进入缓冲区等待下一次剥离。

### 4.3 动态信念修正与知识冲突处理

在长期记忆中，“知识冲突”不可避免，系统将其区分为两种底层逻辑进行处理：

1. **事实的自然演进**：有些冲突本身就是事物随时间发展的客观事实（如从喜欢苹果变成对苹果过敏）。此类信息不视为逻辑错误，系统依靠白描时间戳作为最新状态追加，依靠遗忘机制使旧状态自然衰退。
2. **技术性与代差修正**：有些冲突是技术原因导致的（例如此时的模型推导结论不如将来的模型版本先进）。针对此类认知冲突，仲裁机制应赋予“未来时间点/更先进模型的判断”以绝对的采信权重，直接对旧有认知执行逻辑覆写（Tombstone 墓碑化）。

### 4.4 双流记忆召回机制（Dual-Stream Recall）与代谢演化

回忆块（Recall Block）是 REMS 的核心感知源。系统采用双流检索配合交集优先算法，确保“语义相关”与“角色连贯”的平衡。

- **阶段 1：双流并行检索 (Dual-Stream Search)**：
  - **流 A (基本事件流)**：直接在 `rems_events` 集合中进行向量检索，获取 Top-60 语义相关事件。
  - **流 B (白描流)**：在 `rems_white_paintings` 独立白描集合中检索。该流专门用于从人物侧面反查事件。命中后，系统根据动态 `effective_forgetting` 因子对相似度进行实时削减。已静默（＜0.02）的条目在此阶段被过滤。
- **阶段 2：交集优先合并算法 (Intersection-based Merge)**：
  - **交集优先 (Max 40)**：提取流 A 与流 B 的交集 ID 集合，按最高得分排序选取前 40 条。交集事件同时具备强语义相关性与强人物记忆锚点，是回忆的高地。
  - **余量回填 (10 + 10)**：剩余 10 个名额从流 A 的 Top 列表中选取，另 10 个从流 B 的 Top 列表中选取。若总数不足 60（容量未满），则退化为全量匹配。
- **阶段 3：记忆恢复与加强 (Recovery Logic)**：
  - 成功进入回忆块并输出给下游的事件，其包含的角色白描条目将触发 `forgetting_factor` 恢复逻辑（见 §2.3）。
- **索引层粒度对齐（默认档）**：
  - 无论是基本事件还是抽象事件，写入向量库与回忆展示均默认采用 `summaries[mid_summary_key]`（中位档摘要），避免语义漂移。
- **动态预算分配与降级**：
  - 最终回忆块按 §1.2 动态压缩率执行“懒索引”降级（L1 -> mid -> max summary level），确保在 `1/6.6` 物理红线内最大化信息熵。

## 5. 系统输出机制与多场景架构适配

REMS 作为一个底层代谢架构，不强制绑定单一的响应模式。系统根据不同的商业与应用需求，灵活调整“代谢素材包（回忆块 + 残影 + 当前输入）”的处理管线与输出形态。

### 5.0 模式的边界：只管"输出形态"，不碰"记忆动力学"

所有模式共享一套**强制执行的内部管线**（对应 `REMSPipeline.ingest` 主干）：
1. 组装 `ContextPackage`（回忆块 + 残影 + 当前输入）；
2. 把真实 `event_id` 追加到 `recall_log`；
3. 运行代谢（边界检测、封存、残影维护）、角色更新；
4. 扫全量 `recall_log` 做极大频繁子集挖掘合成抽象事件（§3.2）。

模式差异只在**最后一步——要不要把 ContextPackage 对外暴露、以及是否额外派生指令**。这样设计的刚性理由：
- 抽象事件的**唯一触发路径**是 `recall_log`；如果"静默"模式跳过回忆，系统永远不会演化出归纳规律；
- 语义卡片、AE、白描等巩固机制都依赖检索相关性信号；跳过回忆等于让记忆静态化。

因此"静默倾听"的正确语义是 **"不对用户说话"**，而不是 **"不要构建记忆"**。工程上通过 `ProcessingMode.returns_context_package` 这个布尔属性做路由：True 表示把 ctx 交给上游，False 表示 ctx 留在内部、对外返回 `None`。

### 5.0.1 模式开放性与扩展方法

`ProcessingMode` 枚举当前给出三个内置成员（见 §5.1 / §5.2 / §5.3），但**不是闭合集合**。新增模式时：

1. 在 `ProcessingMode` 枚举中追加成员；
2. 若该模式不向外暴露 ctx（例如"纯归档"、"合规审计"等静默场景），复写 `returns_context_package` 返回 False；
3. 若该模式需要额外的结构化装配（类似 NPC 的 `npc_directives`），在 `ingest` 末端追加一个由 `if mode == …` 触发的装配分支即可；
4. **禁止在新增模式里关闭内部回忆/代谢/抽象三段式**，这是架构不变量。

已规划但未实装的示例模式可包括：`BATCH_INDEX`（离线批量导入，仅沉淀记忆不产出）、`REPLAY_AUDIT`（审计历史回忆轨迹，需要返回 ctx 但不触发 NPC 指令）、`SIMULATED_SELF`（镜像自我对话，既暴露 ctx 也写回新事件）。它们与现有三种模式共享同一条内部管线，只是输出装配策略不同。

### 5.1 场景一：AI 互动对话伴侣（Interactive Dialogue）

对应 `ProcessingMode.DIALOGUE`。这是标准的强输出交互场景（如心理辅导数字人、私人 AI 助理）。

- **拼接与输出逻辑**：系统必须在毫秒级时间内组装完整的 Context Package（即：`回忆块 + 语义卡片 + 残影 + 最新用户输入`）。大模型以此为 Prompt，向用户输出符合角色当前情感量化状态的自然语言回复。
- **后台异步代谢**：在生成回复后，系统在后台对刚才的对话过程进行残影剥离、摘要计算与基本事件的封装入库，不阻塞前台的用户对话体验。
- **模式属性**：`returns_context_package = True`，额外装配 `npc_directives = []`。

### 5.2 场景二：个人生活录音与被动日志提取（Passive Logging）

对应 `ProcessingMode.PASSIVE_LOG`。应用于如穿戴设备录音记录、长期会议监听或个人日志辅助等"只记不说"的场景。

- **拼接与输出逻辑**：该场景下**不需要对输入内容提供任何外部文本输出**。系统对调用方处于"静默倾听"状态，`ingest` 返回的 `context_package` 字段为 `None`。
- **内部仍完整回忆**：即便不对外回复，系统依然会组装回忆块、登记 `recall_log`、触发频繁子集挖掘。这是白皮书唯一承认的抽象合成路径，不能被模式绕过；否则长期被动记录将永远不会产生归纳事件，与 §3 定义冲突。可以把这一层理解为"对用户静默，但对自己的记忆不静默"。
- **后台执行管线**：不存在前台回复步骤。结合 2.2 节的单人模式或多人模式配置，系统接收到长音频转写的文本流后，将其直接送入残影缓冲区。达到 `len_msg` 阈值后自动触发切分、剔除冗余口水话、提取事实生成基本事件、更新时间线白描、在内部回忆驱动下持续产出高阶抽象事件。在此场景下，REMS 纯粹扮演一个高维度的"自治数据库"。
- **模式属性**：`returns_context_package = False`。

### 5.3 场景三：生成式虚拟沙盒与复杂 NPC 生态（Generative Agents）

对应 `ProcessingMode.NPC_AGENT`。应用于开放世界游戏或多智能体模拟环境。

- **拼接与输出逻辑**：环境事件（如"玩家进入酒馆"）作为输入，触发现场所有 NPC 的回忆检索。此时的输出不再是单纯的"对话"，而是被隐性指令转化器（Directive Parser）翻译为具体的**状态机改变或寻路决策**。
- **执行案例**：系统拼接 `回忆块 (玩家曾在村口伤害过该 NPC) + 当前输入 (玩家靠近)`，输出结果直接转化为 NPC 系统底层的行为代码（如 `Action: Flee` 或 `Action: Attack`），并同步提升该 NPC 的 `Klesha_嗔` 维度指标，整个过程无需任何人类可见的文本对话生成。
- **模式属性**：`returns_context_package = True`，额外装配 `npc_directives`（动作 + Klesha/Vedana 增量）供下游 Directive Parser 消费。
