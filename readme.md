# REMS 递归演化记忆系统规范（完整工程版）

本文是在原始核心规范基础上，融合了面向生产环境的动态信念修正、情感遗忘模型、上下文防溢出策略、多场景输出适配、记忆重组机制，以及基于提示词注入的全局代词消解引擎与动态粒度路由的完整工程化技术白皮书。

## 1. 基本事件定义

基本事件（Basic Event）是 REMS 中承载客观事实的最小记忆单元。基于最新的架构逻辑，基本事件不仅记录事实片段，还承载角色在当次事件中的瞬时状态（快照与情感），确保事件的可验证性与主体交互的完整性。

### 1.1 核心属性解析

#### 1.1.1 唯一标识与元数据

- `event_id`：废除传统的字典序生成方式，全面引入**无状态的唯一标识**。系统改用无状态的分布式 ID 生成算法（如 UUID v7、Snowflake 等），消除节点依赖，确保系统内所有事件在分布式环境下的唯一性、可区分性与完全无状态。
- `create_time`：记录事件封装完成的绝对时刻。

#### 1.1.2 原始数据属性

原始数据是基本事件的唯一数据底库，作为记忆系统生成、演化与追溯的绝对事实基准。

- `content_raw`：即 L0 级原始文本。
  - 基本事件：严格等于经剥离并判定为已完成的片段。
  - 抽象事件：由子事件的中位摘要合集集成生成的合成事实描述。

#### 1.1.3 递归摘要体系属性

- `summaries`：以字典形式存储各级递归摘要（L1~Ln）。支持“固定比例压缩”“关键信息提取”或“语义改写”等模式。L1 级实现最大化的“保真压缩”，高阶层级呈现渐进式的抽象梯度。
- `summary_lengths`：以字典形式存储各级摘要对应的字符数。
- `actual_max_level`：受动态熔断机制约束的实际生成层级。

#### 1.1.4 角色交互与瞬时状态属性

通过 `role_list` 记录当次事件中所有参与者的交互细节及量化快照。

- `role_list`
  - `role_id`：关联至角色系统的唯一 ID。
  - `importance`：`S/A/B/C/D` 五级分级。
  - `role_snapshot`：设计为事件中围绕该角色相关信息的 3 个详细程度的白描切片，可通过设定严格的字数预算或语义密度进行工程化控制 ``：
    - **L1（极简白描）**：以极低的字数限制（如 20-30 字）提取核心要素，仅保留实体是否参与及核心动作骨架。
    - **L2（标准白描）**：字数控制在中等范围（如 50-100 字），记录具体的行为逻辑与上下文意图，为系统默认的平衡基准。
    - **L3（详细白描）**：不设严格的字数压缩上限，全量保留角色的详细微观动作、前因后果及环境交互细节。
  - `emotional_model`：记录角色的情感量化状态与波动参数（详细计算逻辑见 2.5 节独立情感与认知调节模块）。

#### 1.1.5 抽象演化与生命周期标记

- `is_abstract`：架构级常量。基本事件固定为 `False`，抽象事件固定为 `True`。
- `is_abstracted`：演化状态位，记录该事件是否已被高阶认知逻辑吸收。
- `status`：反映事件在回忆系统中的权重（未闭环 / 活跃 / 静默）。

#### 1.1.6 扩展属性与规律内核

- `decoration`：针对 `content_raw` 的非事实性描述，支撑“梦见”系统。
- `insight`：基本事件固定为 `None`；抽象事件存储实质性的规律见解或逻辑推导结论。

#### 1.1.7 事件聚合与长度约束属性

- `event_length`：记录 L0 级原始文本的字符长度。
- **物理防御约束**：最高上限设定为 `1/66 * Context_Window`。
- **工程化语义聚合（防碎片化机制）**：对于极其琐碎的短小动作，系统需具备上下文聚合能力，将细粒度连贯动作归于同一个事件中。
  - **判定案例**：当输入为*“我去跑了步，然后就回家了。回家后我打扫了卫生，大概1小时后，看了一会儿小说”*。系统不应将其拆分为四个极短的微小事件，而应在缓冲区聚合封装为单一基本事件：`"content_raw": "用户去跑步后回家，依次打扫了卫生并阅读了一小时小说。"`

#### 1.1.8 抽象事件专用扩展属性

- `abstraction_level`：记录该事件在递归演化树中的深度。
- `source_events`：存储支撑该抽象节点生成的全部子事件 ID 列表。

## 1.2 动态压缩率控制（Dynamic Compression Ratio Control）

为了在有限的上下文窗口预算下精确控制每个事件的「信息膨胀度」，系统引入动态压缩率机制，确保事件代谢所产生的全部衍生数据与原始文本之间维持可控、可预测的比例关系。

### 1.2.1 压缩率定义

- **原始数据长度 `raw_len`**：事件的 `content_raw`（L0 级原始文本）字符长度。
- **衍生数据总长 `sum_len`**：事件封存后产生的全部衍生数据字符数之和，具体包括：
  1. **默认级摘要**：`summaries` 中取中位层级（`mid_summary_key` 对应的级别，如 L2）的文本长度。仅核算系统默认使用的该级别，而非所有摘要级别的总和。
  2. **角色快照（默认级）**：`role_list` 中每个角色的 `role_snapshot` 在默认级别（如 `l2_interaction` 互动白描）的文本长度之和。
  3. **角色白描条目**：写入角色白描时间线的 `WhitePaintingEntry.role_summary` 的文本长度之和（即本次事件向各角色时间线贡献的内容）。
  4. **装饰 `decoration`**：非事实性描述的文本长度。
- **压缩率 `compression_ratio`**：定义为 `sum_len / raw_len`。

### 1.2.2 目标压缩率与预算前置计算

- **目标压缩率**：系统默认维持 `compression_ratio` 约等于 `1/6.6`（约 0.1515）。该比值可通过全局配置 `compression_target_ratio` 调整，以适配不同精度需求的场景。
- **前置预算计算**：由于事件封存的起点是已确定的 `content_raw`，`raw_len` 在调用任何 LLM 之前即为已知量。因此系统在封存流程**最前端**即可确定性地计算出衍生数据的总字符预算，并将其作为硬约束注入后续所有 LLM 调用的提示词中：
  1. **总预算**：`total_budget = raw_len × compression_target_ratio × compression_budget_multiplier`。
  2. **分项预算分配**：总预算按比例分配给各衍生数据项（比例可通过配置调节）：
     - `summary_budget`：默认占总预算的 40%，作为默认级摘要的目标字数上限。
     - `snapshot_budget`：默认占总预算的 25%，由事件中涉及的角色数均分，作为每个角色快照（默认级）的字数上限。
     - `wp_budget`：默认占总预算的 25%，由角色数均分，作为每个角色白描条目的字数上限。
     - `decoration_budget`：默认占总预算的 10%，作为装饰的字数上限。
  3. **提示词注入**：各分项预算以明确的字数约束写入对应技能的 LLM 提示词中（如"请将摘要控制在 XX 字以内"），使大模型在生成时即受预算管控，而非事后裁剪。
- **缩放因子（`compression_budget_multiplier`）**：该乘数用于在目标压缩率的基础上进行全局缩放调节。默认值为 1.0（严格遵循目标比值）。当业务需要更详细的衍生记录时可调高（如 1.5），需要更激进压缩时可调低（如 0.8）。原有的递归摘要熔断（`summary_fuse_min_chars`）、白描粒度路由等既有逻辑保持不变，预算约束通过缩放因子叠加于其上。
- **工程化说明**：预算分项比例不要求每个事件精确遵循，而是作为 LLM 的「建议上限」。当角色数量极少（如仅 1 个角色）时，快照与白描预算可合并使用；当角色数量极多时，单个角色的预算自然收窄以维持总量守恒。

## 2. 角色系统定义与动态遗忘机制

角色系统（Role System）的核心职能是维护全局唯一的角色标识（`role_id`），并将分散在不同基本事件中的事实按时间顺序收集，形成角色的状态机。

### 2.1 角色标识与独立性与“可疑属性”机制

- 角色 ID（`role_id`）是持久化的“容器指针”，用于归集实体行为记录。
- 去代词化映射：强制要求在输入转化为基本事件时，通过 `role_id` 替换模糊代词。
- **历史角色身份仲裁（Entity Resolution）**：回忆块（Recall Block）调出的历史角色如果在语义上与当前新出现的角色存在一致性连结，系统必须执行仲裁确认以判定其是否为同一实体。若判定为同一个角色，系统必须强制复用已有的历史 `role_id`，坚决防止同一个逻辑角色在系统中分裂产生多个截然不同的 ID 副本。
- **角色新增“可疑（Suspicious）”属性**：为应对充满噪声与歧义的文本，角色层级新增“可疑”状态标识。系统仅在以下两条异常途径下将角色标记为“可疑”对象，以备后续修正：
  1. **长度溢界导致强制封装**：当模糊输入长度大幅超界（＞ `msg_len * 1.2`）且必须强制生成事件时，由于无法判断核心身份，系统只能生成临时的对象替代，此时将被打上可疑标记。
  2. **仲裁边界不定**：当系统执行新老指代身份仲裁时难以确信，既不能肯定、也不能轻易否决时，系统将其标记为可疑角色。

### 2.2 全局模式切换与提示词注入引擎（代词消解）

在实际工程落地中，试图在底层代码中穷举所有可能的业务场景缺乏可行性。针对多变语境下的代词（如“我”、“他”）消解问题，系统通过在初始化阶段提供**“单人模式（Single-User）”**或**“多人模式（Multi-User）”**的系统级配置，将环境上下文作为额外信息动态注入到大模型的系统提示词（System Prompt）中，在角色界定与提取时直接指导模型的推理行为。

- **单人模式（Single-user Mode）**
  - **适用边界**：个人备忘录、单主角语音记录、私密生活日志等单一主体的交互环境。
  - **提示词注入策略**：系统后台在封装事件的提示词中明确附加约束条件：“当前系统运行于单人隔离模式。上下文中所有第一人称代词（‘我’、‘我的’）以及缺乏明确主语的动作，均极大可能指向唯一核心用户实体 ``。”
  - **工程优势**：通过模型提示词的硬性约束，极大降低大模型在代词推断上的算力开销与幻觉可能，保障个人上下文的高度一致性。
- **多人模式（Multi-user Mode）**
  - **适用边界**：群组互动、多人会议录音、复杂多 NPC 游戏沙盒等并发环境。
  - **提示词注入策略**：系统在提示词中额外提供环境花名册与消解指令：“当前为多实体交互场景，已知活跃参与者包含 ``。请务必结合对话历史、时间戳与发言者账号/声纹标签，执行精确的多方代词消解（Multiparty Coreference Resolution）。严禁将模糊代词默认归属于单一核心用户。”
  - **工程优势**：将角色排查的任务通过精细化 Prompt 下放给大模型自身的逻辑推理能力，同时为其提供可供比对的实体清单，既保持了架构的简洁，又适应了多线程并行对话的需求。

### 2.3 角色白描系统与动态粒度路由（Chronological White-painting & Granularity Routing）

- **收集与汇编（动态粒度路由）**：系统在将基本事件中的记录汇编到角色白描轴（时间线）时，基于角色权重与运行模式执行动态的详细程度分配：
  - **常规角色（默认提取）**：提取中位层级（L2 标准白描）追加至时间线。这在维持配角状态机连贯性的同时，严格控制了写入体积，防止检索时引发上下文溢出。
  - **主角/单人模式（详细提取）**：若系统处于“单人模式”，或特定 `role_id` 被标记为核心主角，系统将强制拉取 L3（详细白描）。保留最高分辨率的微观动作与上下文细节，能够为大模型提供详尽的具体特征，有效防止长周期交互中的“性格漂移（Personality Drift）”。
  - **白描流水案例**：
    - `ROL-001 (用户/L3级详细白描) 早上 8 点在街角咖啡店购买了一杯深烘焙美式咖啡，并在等待时表现出明显的焦躁。`
    - `ROL-002 (店员/L2级标准白描) 递交咖啡。`

**白描的容量分配与软遗忘机制**：

- **角色容量分配**：系统为每个角色分配一个白描容量上限，其值等于上下文窗口的 `1/6.6` 字符预算（即 `context_chars / 6.6`，与 `len_msg` 同阶）。该容量定义了角色白描时间线在「全保真无遗忘状态」下可承载的最大字符总量。
- **容量内：全量保真**：当某角色的白描时间线总字符长度未超过其容量上限时，系统对该角色的全部白描条目**不施加任何遗忘惩罚**——即所有历史记录以完整权重参与回忆检索与情感查询。
- **容量外：软遗忘启动**：当白描总长突破容量上限后，系统按照**先记录先遗忘（FIFO）**的顺序，从时间线上最早的条目开始逐条施加遗忘因子（基于时间半衰与 AE 的指数衰减系数）惩罚，直到剩余未受惩罚的条目总长回落至容量上限以内。被惩罚的条目在回忆检索的评分阶段中命中概率将大幅降低。
- **物理保留原则**：无论遗忘因子如何衰减，白描条目**在数据库中永远不被物理删除**。这确保了全部历史的可审计性与可追溯性。遗忘在工程上是「影响检索」而非「摧毁数据」。
- 遗忘系数支持根据物理设备（大存储与强算力）或特定业务需求进行全局配置，高保真场景可显著降低遗忘速度。

### 2.4 双轨制认知状态机与语义卡片

- 为彻底根治线性白描带来的检索稀释，系统建立双轨制：在时间线白描外，维护“高密度语义状态卡片”。
- 该卡片存储极致压缩的键值对。
  - **状态卡片案例**：系统将成百上千条白描流水在后台压缩为卡片词典：`{"Role_ID": "ROL-001", "核心偏好": ["深烘焙咖啡", "抗拒酸味"], "性格均值": {"易激惹度": 0.2}}`。在交互中，系统优先拉取该卡片提供绝对基准。

### 2.5 独立情感与认知调节模块（Independent Emotion & Cognitive Modulation Module）

为了科学、可控地计算事件对角色情感的影响，系统剥离了单凭大模型“随意感知”的逻辑，专门设立了基于学术界通用计算标准的独立情感模块。该模块将佛教心理学（五受 Vedana 与六根本烦恼 Klesha）的量化需求，深度挂载到以下两个计算情感引擎中：

- **基于 OCC 模型的基准评估 (Appraisal Framework)**：系统底层采用认知科学中广泛成熟的 **OCC 模型**（Ortony, Collins & Clore）。该模型通过一套确定性的规则，评估当前事件、代理行为和对象对角色内在目标和偏好的影响（Self-appraisal），从而计算出科学、标准化的情感触发基准，防止情感赋予的随意性 ``。
- **基于 EMA 模型的动态演化 (Dynamic Evolution)**：引入 **EMA（情绪与适应，EMotion and Adaptation）模型** 机制。该机制专门用于模拟情感状态（如“嗔”或“苦”）随时间的动态演变。情感量化不仅是静态打分，它会持续评估目标进度与现实预期的差异，并直接干预角色的适应性行为与后续决策 `[1]`。
- **常态默认情感值与记忆存留基准**：情感系统是记忆保留机制的最底层骨架。系统内所有情绪维度的**初始默认值均统一设定为 1.0**。对于极为普通的日常活动（如普通的吃饭、喝水散步等），模型仅赋予 1.0 的平坦情感默认值；此类缺乏情感波峰的琐碎事件仅在短时窗口内可被提取（即短期记得），而在长周期的历史演化中将会被极快速触发衰退并彻底遗忘。
- **与记忆初始值的硬绑定机制**：基于 OCC 与 EMA 双模型的联合计算输出，当某事件引发剧烈的情感波峰（例如极高唤醒度的“极乐”或“大苦”，引发大量偏离 1.0 基础值的溢出参数）时，系统架构将直接把该绝对差映射为极高的“记忆初始值”与“激活能量”。重大情感事件天然获得最强的抗遗忘权重，这为智能体提供了极其真实、不可篡改的心理创伤或高光记忆机制。

## 3. 抽象事件定义与防幻觉规范

抽象事件（Abstract Event）通过对多个低阶事件的归纳，形成具备跨时间属性的高阶认知节点。

### 3.1 核心属性解析

与基本事件保持结构一致，但 `content_raw` 为大模型基于关联事件集（`source_events`）生成的合成事实，`is_abstract` 固定为 `True`。

### 3.2 抽象事件的触发机制

- **召回聚集触发**：某逻辑点召回历史事件超过 5 个，自动启动归并分析生成抽象事件。
- **演化驱动触发**：定期扫描未被吸收的基本事件。

### 3.3 幻觉控制与防强化循环

- **危险的自我强化循环规避**：如果系统仅用于后台记录（无需通过记忆进行预测或对话输出），则不存在该问题。
- 若应用于多轮交互场景，为了防止抽象推演结论被反复当作原始事实入库造成幻觉闭环，系统在后续演化时，将按一定概率强制调用底层事件的“上一级摘要”（而非完全依赖当前的合成文本）进行递归抽象，以确保持续锚定客观事实。

## 4. 事件代谢素材、触发机制与回忆提取规范

### 4.1 残影（Shadow）与未完成事件的精准剥离

- **残影**：存留在系统缓冲区内、未经整理的原始文本素材。
- **未完成事件库**：存储已开启但未闭环的逻辑对象。
- **复杂输入的精准剥离案例**：
  - 当系统接收到输入：*“我去跑了步，然后就回家了。回家后我打扫了卫生，然后继续进行A项目的研发，大概1小时后，看了一会儿小说”*。
  - 判定与剥离逻辑：大模型扫描到“A项目的研发”时，通过检索命中未完成事件库中的历史挂起事件（例如几天前开启的 A 项目逻辑实体）。此时，系统必须精准划开边界：将“打扫卫生”与“看小说”剥离出来作为全新的基本事件封装；将“继续研发A项目 1小时”单独抽离，归入库中已存在的 A 项目未完成事件，更新其完成进度与状态。这种分离机制保证了宏观长期任务与微观即时琐事的物理隔离。

### 4.2 事件的产生条件与模糊截断触发

- **增强型生成前置条件机制**：在判定客观片段是否能够封装为正式事件时，除依赖语义闭环外，必须额外满足以下两个硬性约束条件以拦截无意义碎片入库：
  1. **输入长度底线**：积累的源输入文本长度必须大于 `msg_len / 6.6`，方可考虑作为一个具备宏观记录价值的事件单元落地入库。
  2. **核心角色确定性保障**：对于事件中涉及的主要参与角色，系统必须基本确定其现实身份定位（能够挂载固定的 `role_id` 及清晰的实体面貌）。如果面对模糊或含混的输入，使得系统确认不了核心对象是谁，则尝试悬置为未决片段在缓冲区挂起，不急于生成事件。**底线兜底触发**：若该模糊信息的积累长度已经越过红线界限（逾越 `msg_len` 的 1.2 倍），为防止内存与计算爆炸，系统不再等待，**强制立刻生成事件**；并顺势为该段记录生成临时的、带有“可疑（Suspicious）”属性的角色占位。
- **中间模糊截断机制**：在大模型引导下寻找语义断点，执行约 `0.8 : 0.2` 的比例截断。
  - 工程化说明：此比例不需要绝对精确，只需在阈值附近寻找相对合理的句法停顿即可。因为即使在物理上被生硬截断，最终也可通过后续高阶抽象记忆的重新挂载，让事件在逻辑链条上恢复连贯。截断出的前部分封装入库，剩余部分滞留残影。

### 4.3 动态信念修正与知识冲突处理

在长期记忆中，“知识冲突”不可避免，系统将其区分为两种底层逻辑进行处理：

1. **事实的自然演进**：有些冲突本身就是事物随时间发展的客观事实（如从喜欢苹果变成对苹果过敏）。此类信息不视为逻辑错误，系统依靠白描时间戳作为最新状态追加，依靠遗忘机制使旧状态自然衰退。
2. **技术性与代差修正**：有些冲突是技术原因导致的（例如此时的模型推导结论不如将来的模型版本先进）。针对此类认知冲突，仲裁机制应赋予“未来时间点/更先进模型的判断”以绝对的采信权重，直接对旧有认知执行逻辑覆写（Tombstone 墓碑化）。

### 4.4 两阶段记忆召回机制（Recall）与重组抽象触发（Reconsolidation）

回忆块（Recall Block）不仅是向下索取信息的数据包，更是向上演化抽象规律的驱动引擎。

- **记忆的两阶筛选（执行方式）**：
  当接收到新输入时，系统必须高效检索庞大的历史底库。由于情感能量往往难以依赖单一向量距离衡量，系统采用解耦合的两段式查询管线：
  1. **阶段 1 (海选匹配与遗忘惩罚)**：第一步完全交由底层的纯量化向量数据库完成。使用当前输入（Current Input）和残影（Shadow）作为查询词（Query），利用基础语义空间计算 Top-N 的匹配度。**关键点**：由于随时间衰减的**遗忘因子是一组数值，它非常容易在此环节发挥作用**，系统在此阶段直接将遗忘因子乘加于向量匹配得分之上，在底层海选中剔除了绝大部分已经“被遗忘”的微末记忆。
  2. **阶段 2 (情感精排)**：获取了基础命中的超集后，系统在内存中调取其对应附着的 `情感能量模块（AE）` 和重要度标记等，进行第二次情感权重的精算与结果重排。最终将胜者名单的长度严防死守至 `1/6.6` 上下文主权约束之内，注入给大模型做感知。
- **回忆触发抽象机制（Memory Reconsolidation）**：
  在工程实践中，**回忆是触发抽象事件产生最核心、甚至在多数情况下唯一的途径**。当多个相关的历史基本事件被同一语境重新激活并调取入“回忆块”时，这些记忆进入一种不稳定的“重组（Reconsolidation）”状态。
  - **触发动作**：系统在生成回应的同时，后台异步核查此次提取的同一主题基本事件数量（如 ≥5 个）。此时，大模型利用这批被重新唤醒的记忆组合，强行进行归纳推理，从而生成一条全新的 `is_abstract == True` 的高阶抽象规律（Insight）并落库。

## 5. 系统输出机制与多场景架构适配

REMS 作为一个底层代谢架构，不强制绑定单一的响应模式。系统根据不同的商业与应用需求，灵活调整“代谢素材包（回忆块 + 残影 + 当前输入）”的处理管线与输出形态。

### 5.1 场景一：AI 互动对话伴侣（Interactive Dialogue）

这是标准的强输出交互场景（如心理辅导数字人、私人 AI 助理）。

- **拼接与输出逻辑**：系统必须在毫秒级时间内组装完整的 Context Package（即：`回忆块 + 语义卡片 + 残影 + 最新用户输入`）。大模型以此为 Prompt，向用户输出符合角色当前情感量化状态的自然语言回复。
- **后台异步代谢**：在生成回复后，系统在后台对刚才的对话过程进行残影剥离、摘要计算与基本事件的封装入库，不阻塞前台的用户对话体验。

### 5.2 场景二：个人生活录音与被动日志提取（Passive Logging）

应用于如穿戴设备录音记录、长期会议监听或个人日志辅助等“只记不说”的场景。

- **拼接与输出逻辑**：该场景下**不需要对输入内容提供任何外部文本输出**。系统处于“静默倾听”状态。
- **后台执行管线**：不存在前台回复步骤。结合 2.2 节的单人模式或多人模式配置，系统接收到长音频转写的文本流后，将其直接送入残影缓冲区。达到 `len_msg` 阈值后自动触发切分、剔除冗余口水话、提取事实生成基本事件、更新时间线白描。在此场景下，REMS 纯粹扮演一个高维度的“自治数据库”。

### 5.3 场景三：生成式虚拟沙盒与复杂 NPC 生态（Generative Agents）

应用于开放世界游戏或多智能体模拟环境。

- **拼接与输出逻辑**：环境事件（如“玩家进入酒馆”）作为输入，触发现场所有 NPC 的回忆检索。此时的输出不再是单纯的“对话”，而是被隐性指令转化器（Directive Parser）翻译为具体的**状态机改变或寻路决策**。
- **执行案例**：系统拼接 `回忆块 (玩家曾在村口伤害过该 NPC) + 当前输入 (玩家靠近)`，输出结果直接转化为 NPC 系统底层的行为代码（如 `Action: Flee` 或 `Action: Attack`），并同步提升该 NPC 的 `Klesha_嗔` 维度指标，整个过程无需任何人类可见的文本对话生成。
