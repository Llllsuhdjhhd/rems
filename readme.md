## 1. 基本事件定义

基本事件（Basic Event）是 REMS 中承载客观事实的最小记忆单元。基于最新的架构逻辑，基本事件不仅记录事实片段，还承载角色在当次事件中的瞬时状态（快照与情感），确保事件的可验证性与主体交互的完整性。

### 1.1 核心属性解析

#### 1.1.1 唯一标识与元数据

- **event_id**：废除传统的字典序生成方式，全面引入无状态的分布式 ID 生成算法（如 UUID v7、Snowflake 等），消除节点依赖，确保系统内所有事件在分布式环境下的唯一性、可区分性与完全无状态。
- **create_time**：记录事件封装完成的绝对时刻。

#### 1.1.2 原始数据属性

原始数据是基本事件的唯一数据底库，作为记忆系统生成、演化与追溯的绝对事实基准。

- **content_raw**：即 L0级原始文本。
  - 基本事件：交叉事件被剥离（Disentanglement）后，抽取出的专属于该事件主线的最纯粹原始文本片段（去除干扰和其他事件线内容）。
  - 抽象事件：由其叶子基本事件的 content_raw 拼接为证据后，按基本事件同样的“抓住重点、保留主干”规则压缩生成；目标长度约等于这些基本事件 content_raw 的平均长度。若 source_events 中包含已有抽象事件，系统先展开到叶子基本事件再取其 content_raw，避免基于上一轮抽象文本继续抽象。

#### 1.1.3 递归摘要体系属性 (Recursive Summary Hierarchy)

系统通过同步生成的 L1~L10 摘要来实现记忆的物理压缩与语义浓缩的动态平衡。

- **summaries**：以字典形式存储各级摘要。遵循软性指数衰减原则。
  - 层级预算分配：L1 为最高保真压缩（默认上限为L0长度的1/3），后续层级 $L_n$ 的字数预算遵循 $Budget_n = Budget_{n-1} \times 0.5$ 的递归衰减。
  - **弹性浮动机制**：上述预算为软上限。当摘要为了完成一个语义块的完整表达需要超出预算时，允许向上浮动不超过 30%（即 $Budget_n \times 1.3$）。
  - **双熔断条件（满足任一即停止生成更高一级，2026.05 修订）**：(1) 下一级 $L_n$ 的**预算字数** $\leq$ `summary_fuse_min_chars`（工程默认 35）；(2) 上一级 $L_{n-1}$ 的**实际字数** $\times 0.5$ 小于 $\lfloor \text{summary\_fuse\_min\_chars} \times 0.7 \rfloor$（默认即 < 24 字）。任一条件触发即把当前已产出层级作为最终 summaries 落库，不再继续压缩。第二条用于阻断"上一级本身已压得太短，再砍一半就只剩残句"的劣化场景。
- **summary_lengths**：记录各级摘要的实际字符数，用于代谢评分。
- **actual_max_level**：记录触发停止前的实际最高层级。

#### 1.1.4 角色交互与瞬时状态属性

通过 role_list 记录当次事件中所有参与者的交互细节及量化快照。

- **role_list**
  - **role_id**：关联至角色系统的唯一 ID。若角色身份暂未确定，可能为可疑角色的临时 ID（见 §2.1.1）。
  - **importance**：S/A/B/C/D 五级分级，依据角色在当前事件片段中的**实际戏剧权重**判定，不得基于人物背景或后续情节强行拔高。分级定义严格到位：
    - **S（核心主角）**：其决策直接改变情节走向；若文本中无此类角色，则**不出 S 级**。
    - **A（主要互动对象）**：与主角有直接、关键互动，或在无 S 级时充当主要行动者。
    - **B（次要参与者）**：参与事件但非核心互动方。**反应型角色**（仅提供情绪反应、未通过自身决策推动事件者）**上限为 B 级**，严禁强升 A。
    - **C（在场但无实质参与）**；**D（仅被提及未出场）**。
  - **全叙事层角色覆盖**：角色抽取必须穿透文本所有层级，识别显性与隐性实体，包括但不限于：
    - 直接出场的人物、动物、拟人化对象；
    - 叙事框架中主动发言的第一人称叙述者（如“在下”、“笔者”、“旁白所述”）应登记为可检索的叙述主体；
    - 虽未直接露面，但其行为直接引发当前事件的关键缺席者。
  - **role_snapshot**：角色在当次事件中的瞬时分级切片，**必须严格遵守 L3 → L2 → L1 的“父-子”推导铁律**——即同一事实从最详到最简的层层聚焦，**严禁只是同义改写**。每级回答的问题不同：
    - **L3：详细意图快照**。回答“这个角色的行为全貌是什么？”。必须是一个连贯陈述，包含**深层意图 → 关键动作链 → 直接因果结果**；信息密度最高。
    - **L2：互动逻辑快照**。回答“这个角色在此事件中与他人如何交互？”。必须从 L3 中提取**具体对话回合、动作反馈或情绪回应**。若角色在片段内无对他人交互，则 L2 聚焦其“对所处情境的反应”，而非写“未参与互动”。
    - **L1：骨架白描快照**。回答“这个角色做了一件什么事？”。必须是对 L3 最精炼的结果性总结，仅保留不可再约简的核心事实。
    - *推导示例（武松打虎）*：L3 连贯陈述饮酒、告示、遇虎、搏斗、击杀全链；L2 提取"无视劝阻过冈→遇虎→搏斗→击杀"的互动主线；L1 收束为"武松在景阳冈赤手打死猛虎"。
  - **层级分配策略（硬性、无例外）**：
    - **S 级**：必须生成 L1 + L2 + L3，且体现严格推导关系。
    - **A 级**：必须生成 L1 + L2；L3 **必须留空（设为空字符串 `""`）**。
    - **B / C / D 级**：仅生成 L1；L2 与 L3 **必须留空**。
    - 若文本中确无 S 级角色，所有角色按实际评定的 A/B/C/D 等级执行上述规则，**不得**将任何 A 级强升为 S 级来凑足 L3。
  - **快照字数控制与 L1 熔断**：
    - L3 为最高信息密度档，遵循压缩预算（见 §1.2）。
    - L2 与 L1 按 `snapshot_decay_factor`（默认 0.6）指数递减，即每级相较上一级约减少 40%。
    - L1 **保留与熔断**：若 L1 字数低于 20 字则保留当前文字，不再进一步删减；若 L1 字数低于 10 字且已无实质内容，则将其置为空字符串。
  - **emotional_model**：记录角色的情感量化状态与波动参数（详细计算逻辑见 §2.5 情感表示与遗忘驱动模型）。
- **抽象事件特例**：抽象事件的 role_list 恒为空，不登记 role_snapshot、不登记 emotional_model。但抽象合成输入必须携带基本事件中的角色线索，压缩 content_raw 时不能漏掉关键角色/实体；在需要追溯角色信息时，可通过 source_events 的 BFS 展开直达叶子基本事件获取完整的角色快照（见 §1.1.8）。

#### 1.1.5 抽象演化与生命周期标记

- **is_abstract**：架构级常量。基本事件固定为 False，抽象事件固定为 True。
- **is_abstracted**：演化状态位，记录该基本事件是否已被某条抽象事件纳入 source_events（即已作为子集的一员参与抽象合成）。
- **status**：反映事件在回忆系统中的权重（未闭环 /活跃 / 静默）。

#### 1.1.6 扩展属性与规律内核

- **decoration**：针对 content_raw 的非事实性描述，支撑“梦见”系统。
- **insight**：基本事件固定为 None；抽象事件的 insight 由开关 enable_abstract_insight 控制，默认关闭。开启时仅存储跨事件提炼出的规律/认知结论，不作为事实本身的摘要；关闭时抽象事件只保留 content_raw 与递归摘要。

#### 1.1.7 事件聚合与长度约束属性

- **event_length**：记录 L0 级原始文本的字符长度。
- **物理防御约束**：单条基本事件 L0 的推荐/硬上限约为 `Context_Window × chars_per_token / 66`（工程参数：`len_msg`）。
- **工程化语义聚合（防碎片化机制）**：对于极其琐碎的短小动作，系统需具备上下文聚合能力，将细粒度连贯动作归于同一个事件中。
  - 判定案例：当输入为“我去跑了步，然后就回家了。回家后我打扫了卫生，大概1小时后，看了一会儿小说”。系统不应将其拆分为四个极短的微小事件，而应在缓冲区聚合封装为单一基本事件："content_raw": "用户去跑步后回家，依次打扫了卫生并阅读了一小时小说。"
- **超长未完成事件的三段式防线（替代盲目兜底封存）**：对单条**未闭合事件**累计超过 `len_msg × unclosed_force_ratio`（默认 1.2）红线时，系统按优先级从高到低走三道防线，**禁止**直接对未闭环的超长片段做 `seal_event`（盲目封存会让 Enrichment 在未闭环叙事上产出噪声摘要与错角色）：
  1. **认知层 · 80/20 强制分裂**：边界检测模型在识别到该未完成叙事累计越过红线时，**必须**尝试在最近的逻辑相对闭环处（动作回合收束 / 场景过渡 / 对话告段落 / 情绪收束）把它切成**前段 70%–90%**（目标约 80%）的已闭环前缀事件 + 剩余部分继续作为新的未完成事件；详见 §4.2.4。
  2. **修复层 · 评估器 + 专用分裂 skill**：若模型未切（或切得不达标），规则型评估器（`BoundaryForceThresholdEvaluator`）捕获 `oversized_uc`，随后对每一条越限 UC 独立调用一次 `OverlongUCSplitSkill` 只做"逻辑闭环二切"这一件事；**评估只做一层**，修复器输出不再评估（详见 §4.2.5）。
  3. **物理层 · 红线兜底 force-seal**：仅当上述两道都失败、且残影 + 未完成总长仍越过 `physical_redline`（约 `context_chars × 10/66`）时，系统才对超阈值未完成条目执行强制封存，作为最后的缓冲区防溢出；封存时继承已有的分裂前缀链（见 §1.1.9）。认知层失败的超长 UC 会先以 `oversized=True` 的审计标记保留，不进入第三道防线除非确实挤爆物理红线。

#### 1.1.8 抽象事件专用扩展属性

- **abstraction_level**：记录该事件在递归演化树中的深度（首层抽象 = 1；以抽象事件为成员再次被纳入更高阶抽象时递增）。
- **source_events**：存储触发本次抽象合成的频繁极大子集中的全部事件 ID 列表。该列表的元素可以是基本事件 ID，也可以是已有的抽象事件 ID——抽象事件生成后会以其自身 ID 替换 recall_log 中的原子集，使更高阶抽象在同一命名空间继续演进（详见 §3.2 触发机制）。
- **抽象链反查基本事件**：出于审计、向量检索结果溯源或对话生成时"从规律回到事实"的需要，仓储层提供 EventRepository.resolve_basic_event_ids(event_id)：对 source_events 做 BFS 递归展开（每遇抽象事件就继续下钻），返回该抽象事件传递依赖的全部叶子基本事件 ID 去重列表；若传入的本就是基本事件，则原样返回。因此从任意抽象事件都能在一次调用内拿到其全部事实支撑，包括角色信息。
- **字段缺省**：抽象事件不登记 role_list（恒为空）、不登记 role_snapshot / emotional_model；其 summaries（L1…Ln）由 §1.1.3 递归摘要体系基于 content_raw 正常生成，与基本事件同规则。

#### 1.1.9 80/20 强制分裂链路字段

当超长未完成事件被 §1.1.7 第 1、第 2 道防线切成"前段基本事件 + 后段未完成事件"时，两者之间持有一条显式的双向指针链，供后续闭环继承与回忆端硬性展开使用：

- **`split_prefix_event_ids`**（基本事件与未完成事件都持有，`list[str]`）：**按自远而近**顺序记录本条目所在分裂链中排在它之前的前缀事件 ID。允许 `len ≥ 1`——同一条超长叙事可能跨多轮被切多次，tail 事件最终闭环时把完整前缀链全部继承。
- **`split_successor_event_ids`**（仅基本事件持有，`list[str]`）：反向指针。当某条前缀事件对应的 tail UC 在后续轮次被闭环为正式事件时，新事件的 ID 会被追加到该前缀事件的 `split_successor_event_ids`。允许一个前缀对应多个后继（例如后段又被二次分裂，会产生多条 tail 相继闭环）。
- **回忆端硬性展开**：当某条事件命中回忆并被放进回忆块时，若其 `split_prefix_event_ids` 非空，**所有**前缀事件必须被一并拉进回忆块；允许降档为更压缩的摘要、极端情况下走 `[EVT-xxx] <stub>…` 的 ultra 截断，但**不得丢弃**（详见 §4.4）。
- **链展开深度上限**：为防止跨多轮切分形成的链路撑爆回忆块，沿 `split_prefix_event_ids` 向上展开的最大跳数由 `recall_split_prefix_max_depth`（默认 3）控制；超深度的祖先前缀按"已被抽象合成过"的语义由 §3.2 的抽象事件承载，不再逐跳拉回。
- **与抽象事件的关系**：`split_prefix_event_ids` / `split_successor_event_ids` 仅在基本事件层面维护。抽象事件不参与分裂链；若某条前缀事件被更高阶抽象纳入 `source_events`，其作为前缀的身份不会丢失——回忆端先做前缀展开，再让抽象合成在同一命名空间上运转（见 §3.2）。

### 1.2 动态压缩率控制（Dynamic Compression Ratio Control）

为了在有限的上下文窗口预算下精确控制每个事件的「信息膨胀度」，系统引入动态压缩率机制，确保事件代谢所产生的全部衍生数据与原始文本之间维持可控、可预测的比例关系。

#### 1.2.1 压缩率定义

- **原始数据长度 raw_len**：事件的 content_raw（L0 级原始文本）字符长度。
- **衍生数据总长 sum_len**：事件封存后产生的全部衍生数据字符数之和，具体包括：
  - 默认级摘要：summaries 中取中位层级（mid_summary_key 对应的级别，如 L2）的文本长度。仅核算系统默认使用的该级别，而非所有摘要级别的总和。
  - 角色快照（默认级）：role_list 中每个角色的 role_snapshot 在相应分级（L3/L2/L1+）的文本长度之和。
  - 角色白描条目：写入角色白描时间线的 WhitePaintingEntry.role_summary 的文本长度之和（即本次事件向各角色时间线贡献的内容）。
  - 装饰 decoration：非事实性描述的文本长度。
- **压缩率 compression_ratio**：定义为 sum_len / raw_len。

#### 1.2.2 目标压缩率与动态前置预算

- **目标压缩率（compression_target_ratio）**：系统默认维持 1/6.6（约 0.1515）。
- **短文本宽恕机制（平滑补偿）**：为防止短文本因严格执行压缩率而导致信息丢失，预计算时引入动态补偿：
  ```
  effective_ratio = target_ratio + (1.0 - target_ratio) * exp(-raw_len / 500)





  ```
  当 raw_len 较小时，压缩率自动放宽，允许保留更多细节；当文本较长时，压缩率收敛于 1/6.6。
- **前置预算计算**：在封存流程最前端确定衍生数据总预算：
  ```
  total_budget = raw_len × effective_ratio × compression_budget_multiplier





  ```
- **提示词注入**：预算以硬约束形式注入提示词（如“请将 L1 摘要控制在 XX 字以内”）。
- **缩放因子（compression_budget_multiplier）**：默认值为 1.0。用于全局手动微调。
- **工程化说明**：预算分项比例不要求每个事件精确遵循，而是作为 LLM 的「建议上限」。当角色数量极少（如仅 1 个角色）时，快照与白描预算可合并使用；当角色数量极多时，单个角色的预算自然收窄以维持总量守恒。

## 2. 角色系统定义与动态遗忘机制

角色系统（Role System）的核心职能是维护全局唯一的角色标识（role_id），并将分散在不同基本事件中的事实按时间顺序收集，形成角色的状态机。

### 2.1 角色标识与独立性

- **角色 ID（role_id）**是持久化的“容器指针”，用于归集实体行为记录。
- **去代词化映射**：强制要求在输入转化为基本事件时，通过 role_id 替换模糊代词。
- **历史角色身份仲裁（Entity Resolution）**：回忆块（Recall Block）调出的历史角色如果在语义上与当前新出现的角色存在一致性连结，系统必须执行仲裁确认以判定其是否为同一实体。若判定为同一个角色，系统必须强制复用已有的历史 role_id，坚决防止同一个逻辑角色在系统中分裂产生多个截然不同的 ID 副本。
- **可疑角色**：为应对充满噪声与歧义的文本，角色可能被标记为可疑状态（is_suspicious = True），其详细定义与管理生命周期见 §2.1.1。

#### 2.1.1 可疑角色的判定与解除

**触发条件** 在抽取角色列表时，出现以下任一情况，角色被标记为 Suspicious（is_suspicious = True）：

- **代词无主**：一个动作/对话的参与者无法被可靠地映射到已有 role_id，也无法确定是否应新建 role_id。例如“有人说了一句风凉话”，提炼出一个发言者，但全文没有任何线索能确认这是谁。
- **实体身份冲突未决**：新提取的角色与已有角色在语义上高度相似，但关键属性存在矛盾（如同一姓名但不同的性别描述），系统根据仲裁逻辑无法以高置信度判定是同一人还是同名的两个人。

**存储** 可疑角色与正常角色使用同一存储结构，但 is_suspicious 字段置为 True。其拥有的白描时间线、情感快照等与正常角色一致，但在某些下游应用中可被标记提示。

**确认与解除** 当后续新事件中再次提取到与某个可疑角色语义高度匹配（向量相似度 > 0.95）的实体，且这次能够确定其真实身份时，系统执行解除操作：

- 若判定该可疑角色即某个已存在的正常角色，则将可疑角色的is_suspicious置为false，则即转换为正常的角色。
- 若判定该可疑角色确为一个全新实体，则直接将 is_suspicious 置为 False，转为正常角色。

### 2.2 全局模式切换与提示词注入引擎（代词消解）

在实际工程落地中，试图在底层代码中穷举所有可能的业务场景缺乏可行性。针对多变语境下的代词（如“我”、“他”）消解问题，系统通过在初始化阶段提供 **“单人模式（Single-User）”或“多人模式（Multi-User）”** 的系统级配置，将环境上下文作为额外信息动态注入到大模型的系统提示词（System Prompt）中，在角色界定与提取时直接指导模型的推理行为。

- **单人模式（Single-user Mode）**
  - 适用边界：个人备忘录、单主角语音记录、私密生活日志等单一主体的交互环境。
  - 提示词注入策略：系统后台在封装事件的提示词中明确附加约束条件：
    > “当前系统运行于单人隔离模式。在一般叙述中，第一人称代词（‘我’、‘我的’）指向唯一核心用户。但请注意：当叙述中出现明确引语结构（如‘他说：我觉得……’），引语内部的‘我’指代引述对象而非核心用户。请在处理时先识别引语边界，对边界内的代词恢复模糊消解，结合上下文判定归属，不要一刀切指向核心用户。”
  - 工程优势：通过模型提示词的精细约束，既保证了常规叙述的高效消解，又规避了引语中的错误替换，降低了幻觉可能。
- **多人无主角模式（Multi-user Mode）**
  - 适用边界：群组互动、多人会议录音、复杂多 NPC 游戏沙盒等并发环境。
  - 提示词注入策略：系统在提示词中额外提供环境花名册与消解指令：“当前为多实体交互场景，已知活跃参与者包含 `[实体列表]`。请务必结合对话历史、时间戳与发言者账号/声纹标签，执行精确的多方代词消解（Multiparty Coreference Resolution）。严禁将模糊代词默认归属于单一核心用户。”
  - 工程优势：将角色排查的任务通过精细化 Prompt 下放给大模型自身的逻辑推理能力，同时为其提供可供比对的实体清单，既保持了架构的简洁，又适应了多线程并行对话的需求。
- 保留其他模式的可能

### 2.3 角色白描系统与代谢遗忘 (Chronological White-painting & Metabolic Forgetting)

- **收集与汇编（分级描述密度）**：系统在将基本事件中的记录汇编到角色白描轴（时间线）时，基于角色重要性执行差异化的描述深度：
  - **S 级角色（核心主角）**：提取 L3 级完整快照，包含动机、互动细节、环境反应，形成详尽的白描条目。
  - **A 级角色（主要互动对象）**：提取 L2 级互动白描，记录该角色在事件中的具体言行及对剧情走向的直接影响。
  - **B/C/D 级角色（旁观者、次要互动对象）**：提取 L1+ 级事件级白描，保留其在事件中的具体参与片段（如“角色X 在聚餐中质疑了主角的提议，引发短暂争论后沉默”），写成一句完整的叙述。严格禁止出现脱离具体事件的抽象概括（如“性格急躁”、“向来悲观”）。
  - 单人模式下的核心用户默认视为 S 级；若用户明确将自己设定为次要角色，则依设定降级。
- **动态遗忘因子 (Dynamic Forgetting Factor)**：
  - 每个白描条目（WhitePaintingEntry）均持有 forgetting_factor、base_forgetting_factor 以及 last_accessed_time。
  - **base_forgetting_factor** 的初始化：基于事件对该角色的 **唤醒度（arousal）** 计算（详见 §2.5.3）。唤醒度越高，初始遗忘因子越大，记忆越持久。
  - **指数衰减 (Exponential Decay)**：在回忆检索阶段，系统根据 $t - last\_accessed\_time$ 动态计算衰减后的有效权重（`effective_forgetting`）。该值在底层的数学公式中已自然承载了物理时序衰减。
  - **基于容量排位的动态静默阈值 (Capacity-Ranked Silencing & Recall Speed Control)**：从认知心理学的竞争性记忆痕迹理论（Competitive Trace Theory）出发，遗忘并非达到某个绝对数值，而是基于当前认知负载的末位淘汰。系统将静默阈值定义为**数据库整体容量的存活百分比（例如前 60%）**。系统会持续监控最近一段时间的**回忆速度（即检索响应延迟与处理吞吐量）**：
    - **正常认知负载**：当回忆速度处于健康区间时，系统维持默认的排位阈值（如 Top 60%）。经过时间衰减后，有效权重跌出系统全体数据前 60% 的边缘记忆条目将进入“静默状态（SILENT）”，在向量检索中被物理性过滤，实现生物级遗忘。
    - **高负荷自我保护（遗忘加速）**：当回忆速度过低（即系统出现认知超载、有效检索池过于臃肿）时，系统将动态**收紧存活比例**（例如从 Top 60% 临时压缩至 Top 40%）。这种机制迫使排名靠后的大量次要信息被主动淘汰出活跃记忆区，确保核心心智的回忆速度迅速恢复至健康水位。
    - **工程化落地（2026.05）**：高负荷自我保护由 `rems.observability.PerfMonitor` 触发——它对 `rag_search`（向量检索）/ `recall_assembly`（回忆块组装）/ `abstraction_mining`（频繁子集挖掘）/ `narrative_dedupe`（叙事线判重）等**非 LLM 主算法**的滚动均耗时持续观察，按 phase 的"健康容忍上限 `tolerance_ms`"算 `overload_ratio = mean / tolerance`，整个系统取所有 phase 的最大值并夹到 `[1.0, perf_load_factor_max]` 得到 `load_factor`。
      - 直接驱动力 1：**白描静默阈值**。`DefaultWhitePaintingRetentionStrategy` 读阈值时走 `PerfMonitor.adjusted_silence_threshold(base)`，按 `load_factor` 在 `base` 与 `base × forgetting_overload_silence_boost` 之间线性插值。负载越高 → 阈值越高 → 更多老条目跌进 SILENT，等价于"系统主动遗忘加速"，与上文末位淘汰的语义同构。
      - 直接驱动力 2：**抽象事件叙事线判重比对窗口 K**。详见 §3.2，正常 K=`narrative_dup_compare_recent_k`（默认 200），过载时按 `load_factor` 收紧到 `narrative_dup_min_compare_recent_k`（默认 20），避免把抽象判重再压垮已经卡的检索。
      - 配置侧只需改 `perf_phase_tolerance_ms`：值越大 = 对长耗时任务的容忍度越高 = 越晚进入自我保护；`forgetting_overload_silence_boost` 控制满载时静默阈值的最大倍数。`perf_monitor_enabled=False` 时所有 timer 退化 no-op、`load_factor` 恒为 1.0，便于测试与基线对比。
  - **记忆巩固与长时程增强 (LTP & Memory Consolidation)**：遵循神经科学中的长时程增强效应（Long-Term Potentiation），反复的回忆不仅是读取，更是对神经突触（权重）的物理强化。一旦记忆在回忆块中成功出现，其 `forgetting_factor` 将获得增益强化，**且被允许突破其初始的** `base_forgetting_factor`。
    - **结构性长期记忆转化**：多次成功的提取唤醒会使该条目的有效权重呈现出阶梯式上升。随着提取频率增加，反复被证明有价值的记忆会突破短期缓存极限，最终演化为极难遗忘的结构性长期记忆（如同人类的语义化知识）。
    - **情感催化固化（结合 §2.5）**：回忆时的增益幅度受该条目绑定的初始情感唤醒度（Arousal）深度调节。如果该记忆本身附带极高的高唤醒能量（如强烈的喜悦、恐惧或愤怒），在被二次召回时，其突破基础权重的倍率会显著放大。这在底层复现了人类的“闪光灯记忆（Flashbulb Memory）”或创伤后应激记忆（PTSD）的认知模型——极端情绪事件一旦被回想，会被更为深层地刻画在大脑中。
- **容量外：软遗忘启动**：当白描总长突破容量上限后，系统开始对最早条目施加额外的衰减惩罚。
- **物理保留原则**：无论遗忘因子如何衰减，白描条目在数据库中永远不被物理删除，遗忘仅影响「检索可见性」。

### 2.4 （已删除）双轨制认知状态机与语义卡片

### 2.5 情感表示与遗忘驱动模型

本节定义角色的情感量化表示，以及情感如何驱动遗忘因子初始化与角色状态演化。系统完全摒弃佛教心理学的 11 维复杂模型，采用跨文化验证的 **8 维基本情绪**作为 LLM 输出，并在后端程序内合成为 **唤醒度（arousal）** 与 **效价（valence）** 两个标量。

#### 2.5.1 LLM 输出：8 维基本情绪强度

在角色提取（EventEnrichmentSkill）中，LLM 需为每个角色输出以下 8 种基本情绪的强度值，范围

$$0, 1$$

（0=无，1=极强）。后端程序不要求模型输出 arousal 或 valence。


| 维度  | 英文键            | 说明       | 参与唤醒度计算 | 效价符号 |
| --- | -------------- | -------- | ------- | ---- |
| 愤怒  | `anger`        | 敌对、恼怒、暴怒 | 是       | 负    |
| 恐惧  | `fear`         | 害怕、惊恐、焦虑 | 是       | 负    |
| 喜悦  | `joy`          | 快乐、满足、狂喜 | 是       | 正    |
| 悲伤  | `sadness`      | 失落、抑郁、哀痛 | **是**   | 负    |
| 惊讶  | `surprise`     | 意外、震惊    | 是       | 中性   |
| 厌恶  | `disgust`      | 反感、排斥    | **是**   | 负    |
| 信任  | `trust`        | 接受、安全感   | 否       | 正    |
| 期待  | `anticipation` | 希望、警惕    | 是       | 中性偏正 |


**输出规范**：LLM 严格按照以下 JSON 格式输出（嵌入角色提取结果的 `emotion` 字段）：

```
"emotion": {
  "anger": 0.85,
  "fear": 0.10,
  "joy": 0.00,
  "sadness": 0.30,
  "surprise": 0.00,
  "disgust": 0.00,
  "trust": 0.00,
  "anticipation": 0.20
}
```

若无任何情绪，所有维度填 0。

**核心赋值原则（硬性）**：8 维情绪值**仅依据当前所给文本片段**的动作、语言、心理描写直接推导。**严禁**引入角色的完整生平、后续情节或读者对人物的宏观认知。例如处理"武松景阳冈遇虎"片段时，只关注该段内的动作与心理，不因"武松是好汉"而压低 fear 赋值；处理"宋江浔阳楼题诗"时即便表面豪兴，也要如实标出底色中的 sadness。prompt 内嵌四条经典文学校准样例（武松遇虎 / 宋江题诗 / 契诃夫·万卡 / 黛玉葬花），用于在 LLM 侧校准赋值尺度，实现跨文本稳定打分。

#### 2.5.2 后端合成唤醒度（Arousal）与效价（Valence）

每个事件处理完毕后，程序根据 8 维情绪计算两个标量并存入事件记录和角色快照。

- **唤醒度（arousal）**$a \in [0,1]$：反映情绪的总体激活水平，决定记忆持久性。
  $$a = \max(\text{anger}, \text{fear}, \text{joy}, \text{sadness}, \text{disgust}, \text{surprise}, \text{anticipation})$$
  **认知科学修正**：提取上述高唤醒潜力的主导情绪作为唤醒度基准。除直接的攻防情绪外，极度的悲伤（如重度抑郁或创伤后哀痛）与极度的厌恶（如核心恶心感或道德崩塌）同样能引发极强烈的自主神经与杏仁核活动，必须纳入计算，以支撑创伤性记忆（PTSD）的底层动力学。
- **效价（valence）**$v \in [-1, +1]$：反映情绪的正负性，用于行为决策与对话生成。
  $$v = \frac{ (\text{joy} + \text{trust}) - (\text{anger} + \text{fear} + \text{sadness} + \text{disgust}) }{ (\text{joy} + \text{trust}) + (\text{anger} + \text{fear} + \text{sadness} + \text{disgust}) + \varepsilon }$$
  $\varepsilon = 10^{-6}$ 防止除零。公式自动将结果限制在 $[-1,1]$，且当正负强度相等时输出 0（混合情绪）。

#### 2.5.3 遗忘因子初始化（基于唤醒度）

白描条目（WhitePaintingEntry）的 `base_forgetting_factor` 由唤醒度通过幂函数映射：

$$\text{base\_forgetting\_factor} = 100 \cdot a^{\gamma}, \quad \gamma = 2 \text{（推荐）}$$

映射示例：


| 唤醒度 $a$ | base_factor | 持久性    |
| ------- | ----------- | ------ |
| 0.0（中性） | 0           | 几乎立即静默 |
| 0.2     | 4           | 数小时/天  |
| 0.5     | 25          | 数周     |
| 0.9     | 81          | 近乎永久   |
| 1.0     | 100         | 固化永不遗忘 |


> **可选修正（默认关闭）**：负性效价可额外增强遗忘因子：
>
> $$\text{factor} = 100 \cdot a^{\gamma} \cdot (1 + \alpha \cdot \max(0, -v)), \quad \alpha \in [0, 0.5]$$
>
> 启用时需配置。

#### 2.5.4 角色一段时间内的情感评估

系统维护每个角色的滚动情感状态，用于对话生成和行为决策。

- **指数衰减核**：$\phi(\Delta t) = e^{-\lambda \Delta t}$，$\lambda = 0.1 / \text{小时}$（可配置）。
- **当前平均效价**：
  $$\bar{v}(t) = \frac{\sum_{i=1}^{N} v_i \cdot \phi(t - t_i)}{\sum_{i=1}^{N} \phi(t - t_i) + \varepsilon}$$
- **当前平均唤醒度**：
  $$\bar{a}(t) = \frac{\sum_{i=1}^{N} a_i \cdot \phi(t - t_i)}{\sum_{i=1}^{N} \phi(t - t_i) + \varepsilon}$$
- **累积唤醒能量**（用于触发系统行为）：
  $$E(t) = \sum_{i=1}^{N} a_i \cdot \phi(t - t_i)$$
  当 $E(t) > 5.0$ 时可触发高阶抽象事件生成或状态转换。

若无历史事件，默认 $(\bar{v}, \bar{a}, E) = (0, 0, 0)$。

#### 2.5.5 与原有架构的集成

- **角色快照**：`emotional_model` 字段存储最新的 $(\bar{v}, \bar{a}, E)$ 以及最近事件的原始 8 维向量（可选）。
- **白描条目**：每个条目存储该事件的 `(valence, arousal)` 以及 8 维原始情绪。
- **对话生成**：将 $\bar{v}, \bar{a}$ 注入 prompt，调整回复语气（如高负效价触发共情回复）。
- **回忆检索**：可在双流召回后增加情感相似度重排序（详见 §4.4 Mood-Congruent Memory 逻辑）。

## 3. 抽象事件定义与防幻觉规范

抽象事件（Abstract Event）通过对多次回忆中反复共现的低阶事件子集做归纳，形成具备跨时间属性的高阶认知节点。

### 3.1 核心属性解析

结构与基本事件一致，但存在以下硬性差异：

- **content_raw**：大模型基于 source_events 展开得到的叶子基本事件 content_raw 拼接输入，按基本事件同样的“抓住重点”规则压缩生成；目标长度约等于叶子基本事件 content_raw 均值的 1.2 倍；
- **summaries**：按 §1.1.3 递归摘要体系基于 content_raw 正常生成（L1…Ln + 弹性浮动与 <40字符截止），与基本事件同规则；
- **insight**：由 enable_abstract_insight 开关控制。开启时生成跨事件提炼出的规律/认知结论，不复述事实本身；关闭时不生成；
- **is_abstract**：固定为 True；
- **role_list 恒为空**；抽象事件不登记角色、不生成角色快照、不生成情感量化、不触发任何角色白描追加。合成输入必须带入基本事件的角色线索，压缩 content_raw 时不能漏掉关键角色/实体；当需要角色信息时，可通过 source_events BFS 展开至叶子基本事件获取（见 §1.1.8）；
- **abstraction_level**：记录在递归演化树中的深度，支持抽象事件再作为其他抽象事件的子集成员参与更高阶合成。

### 3.2 抽象事件的触发机制（唯一路径：频繁极大子集挖掘）

抽象事件的合成不再依赖任何向量近邻聚类或定期扫描。其唯一触发路径为：回忆块事件集合中的频繁极大子集挖掘。

- **登记阶段**：每次 RecallService.build_recall_block 成功产出回忆块后，将块内所有真实事件 ID（即 basic 与 abstract，过滤 CARD:* 等伪条目）的有序去重集合，作为一条记录写入 recall_log 表。
- **挖掘阶段**：对 recall_log 的历史记录族 $T_1, T_2, \dots$（每个 $T_i$ 为一次回忆的事件 ID 集合），寻找极大频繁子集 $S$ 满足：
  - $|S| \geq abstract\_subset\_min\_size$（默认 6，可配置，硬门槛防止两三个事件就合成抽象，稀释语义）；
  - 存在 $\mathrm{support}(S) = |\{T_i : S \subseteq T_i\}| \geq abstract\_subset\_min\_support$（默认 5，可配置）；
  - 不存在另一个频繁子集 $S'$ 同时满足 $S \subsetneq S'$（即 $S$ 在频繁集合族内极大，避免同构的小子集重复合成抽象）。
- **合成阶段**：对每个通过阈值的 $S$，以其成员作为 source_events；调用归纳演化技能（InductiveEvolutionSkill）时先将成员递归展开到叶子基本事件，拼接这些基本事件的 content_raw 与角色线索作为输入，合成压缩后的抽象事件 content_raw；持久化后调用 §1.1.3 的 SummaryGenerationSkill 为其 content_raw 生成多级摘要与 actual_max_level，再索引入向量库。
- **幂等 & 同名空间迭代（抽象事件可再次抽象）**：
  - 每条抽象事件生成后会把其指纹（$S$ 成员排序后拼接）登记到 abstracted_subsets 表，同一 $S$ 不会被重复合成；
  - 生成后会遍历所有满足 $S \subseteq T_i$ 的历史 recall_log 行，将其中的 $S$ 成员移除，插入新抽象事件 ID。“用抽象事件 ID 代替原来的子集”使得挖掘逻辑在单一命名空间内统一：后续回忆块若仍然整体命中该抽象事件，会与历史记录在同一空间里累积支持度；若多个已合成的抽象事件再度频繁共现，即触发更高阶抽象（source_events 可直接嵌套抽象事件 ID，abstraction_level 递增），自然形成多阶演化树；
  - source_events 内的基本事件会被标记 is_abstracted = True（仅基本事件；嵌套的抽象事件不做此标记，因为它们本身也是高阶演化的中间节点）；
- **从抽象反查基本事件**：需要溯源到事实层时，调用 EventRepository.resolve_basic_event_ids(event_id) 即可沿整条 source_events 链路 BFS 展开到叶子基本事件，无论抽象有多少层（见 §1.1.8）。这使得“规律 → 事实”的检索在任意阶抽象上都保持 O(1) API。

#### 3.2.1 抽象事件叙事线判重（2026.05 新增）

`mine_and_synthesize` 内部按以下顺序串接三道去重护栏，覆盖从"字面相同"到"叙事相似"的全谱系：

1. **`is_fired(subset)`**：字面完全相同的子集直接拦截（旧机制）。
2. **`replace_subset(...)`**：新抽象事件登记后，把所有"完全包含 $S$"的 recall_log 行原子级改写——把 $S$ 的成员替换为新抽象 ID，下一轮 mining 时同一叙事线不再以同样的子集形态被挖出（旧机制）。
3. **`_is_narrative_duplicate(subset)`**（**新增**）：拦截 1、2 之间的灰区——subset 与某条已有抽象事件 $A$ 的**叶子**集合（含嵌套抽象的 BFS 展开）在叙事线层面高度重合：
   - $\mathrm{overlap} = |S \cap A.\mathrm{leaves}| / |S| \geq$ `narrative_dup_overlap_threshold`（默认 0.9）；
   - 同时新增信息**不显著**：$\mathrm{novelty\_ratio} = |S \setminus A.\mathrm{leaves}| / |S| <$ `narrative_dup_novelty_min_ratio`（默认 0.1） **或** $\mathrm{novelty\_abs} <$ `narrative_dup_novelty_min_abs`（默认 2）；
   - 任一条件成立则跳过新合成，并把这条 subset 以 `matched_id`（被命中的 A）登记到 `fired_repo`，避免下一轮反复挖到再走一次判重。

**护栏意义**：单独看 overlap 比例会被"短子集差 1 个"骗过（5/6=0.83 ≈ 边界），单独看绝对量会让"长 subset 加 1 个新事件"被误放过；两者**同时**满足才视作"老素材新叙事"（白皮书 §3 关于"同一基础事件可在多条叙事线上独立抽象"的语义）。

**性能护栏**：候选 × 已有抽象的全比成本随抽象规模线性增长。判重默认只与最近 K = `narrative_dup_compare_recent_k`（默认 200）条已合成抽象比对。当 §2.3 `PerfMonitor` 检测到 `narrative_dedupe` / `abstraction_mining` 等 phase 越线时，K 按 `load_factor` 线性收紧到 `narrative_dup_min_compare_recent_k`（默认 20），保证至少 1 条比对、避免在已经卡的算法上再花算力。

### 3.3 幻觉控制与防强化循环

- **危险的自我强化循环规避**：如果系统仅用于后台记录（无需通过记忆进行预测或对话输出），则不存在该问题。
- 若应用于多轮交互场景，为了防止抽象推演结论被反复当作原始事实入库造成幻觉闭环，归纳演化技能在合成时始终展开到叶子基本事件，并以基本事件 content_raw（而非中间级摘要或上一轮抽象文本）作为证据输入。抽象事件参与更高阶合成时同样先反查到基本事实层。

## 4. 事件代谢素材、触发机制与回忆提取规范

### 4.1 残影（Shadow）与未完成事件的统一定义

- **残影**：系统中所有未完成事件内容的物理拼接。它不再作为独立的缓冲区存在，而是未完成库在原始文本层面的“视图（View）”。
- **未完成事件库**：存储已开启但未闭环的逻辑对象（`UnclosedEvent`）。关键字段：
  - `content_fragments`：按时间累加的片段列表，`merged_content` 为拼接后的原文；
  - `logical_gaps`：模型识别出的"仍缺什么"的自然语言描述；
  - **`split_prefix_event_ids`**：若本条是某次 80/20 强制分裂的"尾段"，记录它前面的前缀事件链（自远而近）。UC 最终闭环为事件时该链会被完整继承到新事件的 `split_prefix_event_ids`，并同时反向写入每个前缀事件的 `split_successor_event_ids`（见 §1.1.9）。
  - **`oversized`**：审计标记。当评估器判定该 UC 累计已越过 `len_msg × unclosed_force_ratio` 红线、且认知层修复 skill 也放弃切分时，该条 UC 以 `oversized=True` 原样保留在库中——**不**走 `seal_event`；仅在物理红线（`physical_redline`）被真正触发时，由 §4.2 最后一层兜底 force-seal（此时封存事件仍会继承已有前缀链）。
- **动态关系**：
  - 输入摄入时，系统提取所有未完成事件并拼接为残影。
  - 回忆检索与边界检测均以"残影 + 最新输入"作为全文上下文。
  - 边界检测剥离出"已闭环事实"（封存为基本事件，包括 80/20 分裂的**前缀事件**）与"新/后续未完成片段"（包括分裂的**尾段 UC**，携带前缀链）。
  - 代谢完成后，残影根据更新后的未完成库重新生成。
- **复杂输入的精准剥离案例**：
  - 当系统接收到输入：“我去跑了步，然后就回家了。回家后我打扫了卫生，然后继续进行A项目的研发，大概1小时后，看了一会儿小说”。
  - 判定与剥离逻辑：大模型扫描到“A项目的研发”时，通过检索命中未完成事件库中的历史挂起事件（例如几天前开启的 A 项目逻辑实体）。此时，系统必须精准划开边界：将“打扫卫生”与“看小说”剥离出来作为全新的基本事件封装；将“继续研发A项目 1小时”单独抽离，归入库中已存在的 A 项目未完成事件，更新其完成进度与状态。这种分离机制保证了宏观长期任务与微观即时琐事的物理隔离。

### 4.2 事件剥离与序号编码协议、语义闭包与碎屑代谢

为了最大限度优化模型在代谢过程中的 Token 消耗并维持回忆上下文的纯净度，系统全面采用 Sentence-ID Encoding（序号编码）协议，并引入严密的“语义闭包”与“碎屑代谢”机制。

#### 4.2.1 语言学视角的边界界定与“语义闭包 (Semantic Closure)”

- **分句索引化**：系统将一段充满冗余、交叉的残影（Shadow）文本预先进行语义分句，并标记为 `[序号]` 文本格式。同时在 prompt 中显式标注"既有残影序号区间"与"本轮新输入序号区间"，防止模型把两者混为一段。
- **零文本返回与语义闭包约束**：在剥离事件（Disentanglement）时，大模型通过返回对应的句序列表 `content_raw_indices`（例如 `[1, 2, 5]`）来界定范围，禁止返回原文 text。
  - **闭包校验规则**：大模型在挑选序号时，必须保证所选序号构成一个**“语义闭包”**。即：如果句 5 存在对句 4 的强依赖指代（如代词“他”、“然后”等衔接成分），则句 4 和句 5 绝对不可被割裂。剥离出的事件必须在孤立状态下具备完整的主语、谓语及语境连贯性。
  - **续写判定**：若当前片段是未完成事件库中某条的续写，在对应 completed 片段上填写 `continuation_of = "UC-xxx"`；闭环后该 UC 被删除，其内容与当前片段合并为新基本事件。
- **物理还原逻辑**：系统在接收到模型返回的索引序列后，在本地（EventService）直接根据索引碎片还原出完整的 `content_raw`，消除了模型搬运原文产生的幻觉（漏删、错字）。

#### 4.2.2 心理学与 AI 视角的“饼干碎屑 (Cookie Crumbs)”处理机制

在执行完主事件剥离后，未被选中的剩余序号文本（如上例中的句 3、句 4）若无法独立成事，即沦为残缺的“碎屑”。若任由碎屑在残影库累积，将导致大语言模型的上下文注意力崩溃（Attention Pollution），并严重污染后续的实体回忆块。为此引入以下三段式代谢：

- **机制 1：向上吸收 (Semantic Absorption)**
  - 在**剥离事件（BoundaryDetection）的过程中，大模型在挑选主干序号时，若检测到相邻的“碎屑”仅仅是对主事件的微小心理反应或环境描写（如“当时风很大”、“我感到一阵疲惫”），这些碎屑禁止**被遗弃在残影缓冲区。它们必须被直接**“向上吸收”（合并选中）**，作为附属序号一并返回，以便将其合并打包到完整的 `content_raw` 中，从而彻底清空缓冲区的冗余碎片。
- **机制 2：影子降噪压实 (Shadow Compaction)**
  - 为了防止 AI 在下一次解析时面对支离破碎的半截病句，当残影缓冲区内的碎片数量达到一定阈值（或呈现明显的语法断层）时，触发“压实”指令。调用 LLM 将当前的残影碎片重新用平滑的自然语言改写为连贯的背景状态描述，消除语法孤儿，确保输入给下一轮代谢的上下文始终纯净。
- **机制 3：无主碎屑的垃圾回收 (Garbage Collection / Trace Decay)**
  - 模拟人类大脑工作记忆的痕迹衰退（Trace Decay）。为残影库中的独立碎屑分配生命周期（TTL）。如果某段碎屑在连续 $N$ 轮交互或经过一定时间跨度后，仍未能与新输入拼接成闭环事件，系统将判定其为毫无价值的背景噪音，并将其物理抹除。坚决避免无主碎片长期挂起并拉偏后续人物召回的向量检索方向。

#### 4.2.3 剥离与代谢的工程管线整合

架构层面允许「剥离 + 摘要 + 角色」在一次 LLM 调用中完成。本参考实现出于 prompt 噪声控制与角色抽取稳定性考虑，将其拆分为两步：

- BoundaryDetectionSkill：执行序号剥离、校验语义闭包、执行"碎屑向上吸收"（将环境/心理等微小描述合并入选中的序号中）、判断残影与未完成事件、**执行 80/20 强制分裂（§4.2.4）**；
- EventEnrichmentSkill：基于包含已吸收碎屑的完整 `content_raw`，按以下三种工作模式之一产出摘要 / 角色，同时将环境/心理描写结构化写入 `decoration` 字段。
- **超长未完成的三段式兜底（取代原有盲目 force-seal）**：当单条未闭环片段累计越过 `msg_len × unclosed_force_ratio` 红线时，系统**禁止**直接调用 `seal_event`。顺序为：(1) 认知层 80/20 分裂（§4.2.4）→ (2) 评估器 + 专用修复 skill（§4.2.5）→ (3) 物理红线 force-seal（仅作为缓冲区防溢出）。在第 (1)(2) 层失败但尚未击穿物理红线时，UC 以 `oversized=True` 审计标记原样保留在库中。

##### 4.2.3.1 EventEnrichmentSkill 三种工作模式（2026.05 修订）

`EventEnrichmentSkill.enrich(...)` 根据上游传入的角色信息形态在三种模式中路由（优先级 `skip_roles` > `names_only` > `full`）：

| 模式 | 触发条件 | LLM 输出 | snapshot / 8 维情绪来源 |
|---|---|---|---|
| `full` | `pre_role_entries` 为空（pre-recall 未抽到角色）且未 `skip_roles` | 摘要 + **完整角色**（含 snapshot + 8 维情绪） | LLM 同次产出 |
| **`names_only`（默认对话流）** | pipeline pre-recall 已经抽到角色，把 `role_entries`（含 snapshot + 8 维情绪）作为「全局富信息池」下放 | 摘要 + **本事件实际登场的角色名字符串数组**（如 `["贾雨村", "娇杏"]`）；不出 `role_id` / snapshot / emotion | 后端用名字对 `known_roles`（含 aliases）做**字符串匹配**解析 `role_id`，再从 pre-recall 池回填 snapshot + 8 维情绪 |
| `summary_only` | 外部已经显式构造了完整 `role_entries` 或显式 `skip_roles=True` | 仅摘要 | 由调用方提供 |

`names_only` 路径的设计动机：pipeline pre-recall 阶段已经在 `shadow + raw_input` 完整上下文上调用 `RoleExtractionSkill` 抽出过一份"全局角色池"，每个角色的 snapshot 与 8 维情绪都基于完整上下文判定；事件级 enrichment 只需要回答"这条 sealed event 里**实际登场**了池中哪些角色"——一个轻量的"摘要 + 角色名字符串数组"调用就够了，避免为每条事件让 LLM 把 snapshot/情感重做一遍。

`names_only` 的 LLM 契约（与 `full` 路径一同输出 role_id + 各级 snapshot + 8 维 emotion 的对比）有意只让模型出名字数组，**`role_id` 完全由代码用字符串匹配解析**：把 `known_roles.name` 与 `known_roles.aliases` 全量摊平成 `name → role_id` 字典，命中即取池中富信息条目；prompt 端要求 LLM 命中已知角色时**输出该角色在已知列表里的规范名**（"雨村" → "贾雨村"），降低匹配失败概率。

事件最终 `role_list` 仍只包含本事件真实出场的角色子集，富信息从池里直接复制；池外新角色（极少数 pre-recall 漏抽场景）走兜底路径自动注册并以空快照入库（带 `info` 日志）。

数据下放路径：`REMSPipeline.ingest` → `MetabolismService.process_input(pre_role_entries=role_entries)` → `_apply_boundary_result` / `_force_save_all` → `EventService.seal_event(pre_role_entries=...)`，最终在 `seal_event` 里完成模式选择与池回填。

#### 4.2.4 超长未完成事件的 80/20 强制分裂（Forced Split at Logical Closure）

针对未闭环叙事"越聊越长但始终不结案"的长上下文病态（典型：长篇小说叙事、会议实录），系统要求边界检测模型在识别到某条未完成叙事累计越过 `force_threshold = msg_len × unclosed_force_ratio`（默认 1.2）时，**必须**在**最近的逻辑相对闭环处**（动作回合收束 / 场景过渡 / 对话告段落 / 情绪收束）把它切成两段，而不是机械按字数硬切。

- **分裂比例**：前段长度目标约 **80%**（可接受区间 70%–90%，由 `boundary_split_ratio_*` 配置）；
- **前段语义**：构成一个相对独立的逻辑闭环，可独立理解、可独立封存为一条基本事件；
- **后段语义**：继续作为新的未完成叙事挂起；
- **配对声明**：前后两段在同一次模型返回中通过一个自造的 `split_id`（形如 `"SP-1"`/`"SP-2"`，同一响应内唯一）显式配对；系统借此把前缀事件 ID 回填到后段 UC 的 `split_prefix_event_ids`（见 §1.1.9）。

**边界检测 JSON 输出字段表（2026.05 修订）**：

```json
{
  "completed_events": [
    {
      "content_raw_indices": [1, 2, 5],
      "continuation_of": "UC-xxx 或 null",
      "is_split_prefix": false,
      "split_id": null
    }
  ],
  "new_unclosed": [
    { "indices": [12, 13], "split_id": null }
  ]
}
```

| 字段 | 归属 | 含义 |
|---|---|---|
| `content_raw_indices` | completed | 事件命中的句子序号列表（零文本返回） |
| `continuation_of` | completed | 续写目标 `UC-xxx`，闭环后该 UC 被删 |
| `is_split_prefix` | completed | 是否是某次强制分裂的 80% 前缀 |
| `split_id` | completed / new_unclosed | 分裂配对 ID；两侧必须成对出现 |
| `indices` | new_unclosed | 该未完成事件命中的句子序号列表 |
| `logical_gaps` | new_unclosed（可选） | 模型识别的"仍缺什么" |

兼容性：旧格式 `new_unclosed_indices: [12, 13]`（扁平）或 `[[12,13],[20,21]]`（嵌套）仍被解析，但该路径**无法**声明 `split_id`，故不会触发分裂配对；需要配对时必须使用新的 `new_unclosed` 对象写法。

#### 4.2.5 通用 Skill 评估 / 修复协议（Evaluation & Remediation）

对每个 LLM 技能的输出，系统都可以挂接**评估器（SkillEvaluator）**与**修复器（SkillRemediator）**，形成"调用 → 评估 → 必要时修复"三段式。协议硬性约束：

1. **评估只做一层**。修复器返回的新输出**不再**进入评估，防止"评估-修复-评估-修复"的无限递归。
2. 一次 skill 调用可挂多个评估器，按**严格合并**（任一失败 → 整体失败）聚合报告；修复器只有一个。
3. 评估器可以是**规则型**（零 LLM 成本、始终开启）或**LLM 型**（使用另一模型对本次输出进行打分评价；默认关闭，成本敏感）。
4. 修复器可以是"同 skill 再跑一次带额外参数"，也可以是一个**独立的窄范围 skill**（只做一件事，便于快速收敛）。
5. 评估失败且修复失败时，调用方按"降级保留"策略处理——**不**把责任推给下游 `seal_event` 等高代价组件。

对应到 BoundaryDetection 的配置：

- **评估器**：`BoundaryForceThresholdEvaluator`（规则型，默认启用）。检查
  - `oversized_uc`：任一 `new_unclosed` 越过 `force_threshold` 且未声明 `split_id`；
  - `split_tail_still_oversized`：已配对但尾段本身仍越阈值；
  - `broken_split_pair`：两侧 `split_id` 不一一配对（孤儿前缀 / 孤儿尾段）；
  - `split_ratio_off`：分裂比例显著偏离区间，仅 warn 级别，不阻塞。
- **修复器**：`OverlongUCSplitRemediator`（默认启用，`boundary_remediation_enabled`）。对每一条越限 UC 独立调用一次 `OverlongUCSplitSkill`（只做"逻辑闭环二切"这一件事，prompt 直接给原文不走句子编码），把原条替换为"`completed_events` 新增一条带 `split_id` 的前缀 + `new_unclosed` 替换为带同一 `split_id` 的尾段"。修复器会做原文字符等价校验（防止 LLM 改写）与比例硬防线（超出 ±5% 立即放弃）。
- **全部失败的兜底**：越限 UC 原样保留 + `oversized=True`；等 §1.1.7 第三道物理红线触发时再强制回收。

协议是 skill-agnostic 的——`EventEnrichmentSkill`、`InductiveEvolutionSkill` 等可复用同一套接口挂接自己的评估器（如"角色列表为空但原文出现角色"、"抽象 `content_raw` 超目标 2×"等）。

### 4.3 动态信念修正与知识冲突处理

在长期记忆中，“知识冲突”不可避免，系统将其区分为两种底层逻辑进行处理：

- **事实的自然演进**：有些冲突本身就是事物随时间发展的客观事实（如从喜欢苹果变成对苹果过敏）。此类信息不视为逻辑错误，系统依靠白描时间戳作为最新状态追加，依靠遗忘机制使旧状态自然衰退。
- **技术性与代差修正**：有些冲突是技术原因导致的（例如此时的模型推导结论不如将来的模型版本先进）。针对此类认知冲突，仲裁机制应赋予“未来时间点/更先进模型的判断”以绝对的采信权重，直接对旧有认知执行逻辑覆写（Tombstone 墓碑化）。

### 4.4 双流记忆召回机制（Dual-Stream Recall）与代谢演化

回忆块（Recall Block）是 REMS 的核心感知源。系统摒弃了单一且脆弱的硬交集逻辑，采用包含 RRF 融合与无量纲平滑修饰的动态重排架构，以确保“语义相关”、“角色连贯”、“记忆巩固度”以及“情绪一致性”的物理与数学平衡。

- **阶段 1：双流并行检索 (Dual-Stream Search)**：
  - 流 A (基本事件流)：直接在 rems_events 集合中进行向量检索，获取 Top-60 语义相关事件。系统在此模拟人类“发生过什么事”的情景记忆读取。
  - 流 B (白描流)：在 rems_white_paintings 独立白描集合中检索人物轨迹线，映射回对应的事件 ID。该流专门用于从人物侧面（谁牵涉其中）反向激活事件。命中后，系统根据动态 `effective_forgetting`（已包含物理时序衰减）因子对相似度进行实时削减。已静默（有效权重低于阈值）的条目在此阶段被绝对过滤。
- **阶段 2：无量纲动态融合重排算法 (Dimensionless RRF & Bounded Modifiers)**：
  为彻底解决绝对分跨度过大带来的“乘法失真（量纲灾难）”，系统抛弃原始余弦相似度绝对值，以名次（Rank）计算基准分，并采用平滑有界对数函数（Squashing Function）进行乘数约束。最终截取 Top 60：  
  `Final Score = RRF_Score * Factor_Modifier * Mood_Modifier`
  1. **基准分：倒数秩融合 (RRF Score)**：  
  $RRF\_Score = \frac{1}{k + Rank_A} + \frac{1}{k + Rank_B}$（常数 $k$ 默认取 60）。  
  若事件仅出现在单一流中，未出现的流 Rank 视为无穷大（得分为 0）。RRF 将所有底层的向量得分严格归一化到了一个极其微小且平滑的安全区间（约 $[0, 0.033]$），作为修饰倍数的基座。
  2. **遗忘因子增益平滑修饰 (Factor Modifier)**：  
  底层的 `effective_forgetting` 既承载了绝对时序的指数衰减，又承载了 LTP 记忆巩固。为了不让极端巩固的记忆（如权重高达 150）在乘法中失真，引入对数约束算法将其转化为一个有界乘数：  
  $Factor\_Modifier = 1.0 + \alpha \cdot \log_{10}(1 + effective\_forgetting)$（其中 $\alpha$ 为控制增益幅度的超参，如 0.5）。  
  这使得高度巩固的记忆能获得 1.x 倍到 2.x 倍的温和奖励，而不是粗暴地放大百倍，确保“语义与角色名次”永远是检索排位的核心基石。
  3. **情感共振修饰 (Mood Modifier)**：  
  提取该候选记忆的原始效价 $(v)$，与实体当前的滚动情绪效价 $(\bar{v})$ 进行极性校验。若效价同号（例如处于愤怒状态时检索到了令人愤怒的历史事件）：  
  $Mood\_Modifier = 1.0 + \beta \cdot (v \times \bar{v})$（$\beta$ 默认 0.2）。  
  否则 $Mood\_Modifier = 1.0$。这使得底层检索动态拟合生物大脑“心境状态依赖”的提取倾斜。
- **阶段 3：记忆加强与情绪脱敏 (Consolidation & Habituation)**：
  成功进入回忆块并输出给下游的事件，将触发双重代谢反馈：
  1. **语义事实固化 (LTP)**：该条目的 `forgetting_factor` 获得显著恢复，甚至突破基础值（长时程增强，见 §2.3），强化其结构性长期记忆的地位。
  2. **情绪脱敏 (Habituation/Extinction)**：该记忆条目绑定的初始情感强度参数 $(v, a)$ 将触发微量衰减折扣（如每次提取下降 1%）。这一机制完美模拟了心理学中“时间冲淡了情绪刺激，但反复提取固化了客观事实”的神经习惯化过程。
- **索引层粒度对齐（默认档）**：
  - 无论是基本事件还是抽象事件，写入向量库与回忆展示均默认采用 summaries 的中位档摘要，避免语义漂移。
- **动态预算分配与降级**：
  - 最终回忆块按 §1.2 动态压缩率执行“懒索引”降级（L1 -> mid -> max summary level），确保在 1/6.6 物理红线内最大化信息熵。

#### 4.4.1 80/20 分裂前缀的硬性展开（Split-Prefix Expansion）

当某条被召回事件 E 的 `split_prefix_event_ids` 非空时，说明 E 是一段超长叙事的"尾段闭环事件"，它前面的所有前缀事件构成不可切断的叙事链（见 §1.1.9）。在 `_assemble_block` 完成后、返回调用方之前，系统执行一道**硬性展开**：

1. **必现**：E 的 `split_prefix_event_ids` 中的每一条前缀事件，**必须**出现在最终回忆块中——无论它们自己是否直接命中语义/白描检索。
2. **时间语序**：前缀事件按"自远而近"顺序排在 E 之前；若某条前缀本身也有前缀链（多跳），其祖先前缀先于它出现。即便某条前缀恰好已被 RRF 排在 E 之后进入 block，系统也会把它**重排**到 E 之前，保留叙事可读性。
3. **允许降档，禁止丢弃**：新追加的前缀事件初始以"比默认档再压一级"的摘要落块；若累加后越过 `physical_redline`，系统只会把**前缀事件**降级到 ultra-concise（`[EVT-xxx] <stub>…`）形态，**锚定事件**（E 本身及其它正常命中事件）保持原档。任何情况下前缀事件都带 `event_id`，可追溯。
4. **链深度上限**：沿 `split_prefix_event_ids` 向上展开的最大跳数由 `recall_split_prefix_max_depth`（默认 3）控制。超深度的早期前缀按"已被抽象合成承载"的语义交由 §3.2 频繁极大子集挖掘去覆盖，不再逐跳回拉。
5. **去重**：同一前缀事件在多条命中事件间共享时，只入一次。

语义目标：用户的原始长叙事即便被 80/20 切成多段，也能在单次回忆中被完整再现——不会出现"只看到收尾、前面的铺垫全丢"的认知断层。

## 5. 系统输出机制与多场景架构适配

### 5.-1 参考环境

本参考实现当前以 Python 3.12 为主环境验证。推荐使用 conda 创建隔离环境：

```
conda create -n py3125 python=3.12.5
conda activate py3125
python -m pip install -e ".[dev]"
```

REMS 作为一个底层代谢架构，不强制绑定单一的响应模式。系统根据不同的商业与应用需求，灵活调整“代谢素材包（回忆块 + 残影 + 当前输入）”的处理管线与输出形态。

### 5.0 模式的边界：只管"输出形态"，不碰"记忆动力学"

所有模式共享一套强制执行的内部管线（对应 REMSPipeline.ingest 主干）：

1. 组装 ContextPackage（回忆块 + 残影 + 当前输入）；
2. 把真实 event_id 追加到 recall_log；
3. 运行代谢（边界检测、封存、残影维护）、角色更新；
4. 扫全量 recall_log 做极大频繁子集挖掘合成抽象事件（§3.2）。

模式差异只在最后一步——要不要把 ContextPackage 对外暴露、以及是否额外派生指令。这样设计的刚性理由：

- 抽象事件的唯一触发路径是 recall_log；如果"静默"模式跳过回忆，系统永远不会演化出归纳规律；
- 白描、情绪遗忘与抽象巩固机制都依赖检索相关性信号；跳过回忆等于让记忆静态化。

因此"静默倾听"的正确语义是 "不对用户说话"，而不是 "不要构建记忆"。工程上通过 ProcessingMode.returns_context_package 这个布尔属性做路由：True 表示把 ctx 交给上游，False 表示 ctx 留在内部、对外返回 None。

#### 5.0.1 模式开放性与扩展方法

ProcessingMode 枚举当前给出三个内置成员（见 §5.1 / §5.2 / §5.3），但不是闭合集合。新增模式时：

- 在 ProcessingMode 枚举中追加成员；
- 若该模式不向外暴露 ctx（例如"纯归档"、"合规审计"等静默场景），复写 returns_context_package 返回 False；
- 若该模式需要额外的结构化装配（类似 NPC 的 npc_directives），在 ingest 末端追加一个由 if mode == … 触发的装配分支即可；
- 禁止在新增模式里关闭内部回忆/代谢/抽象三段式，这是架构不变量。

已规划但未实装的示例模式可包括：BATCH_INDEX（离线批量导入，仅沉淀记忆不产出）、REPLAY_AUDIT（审计历史回忆轨迹，需要返回 ctx 但不触发 NPC 指令）、SIMULATED_SELF（镜像自我对话，既暴露 ctx 也写回新事件）。它们与现有三种模式共享同一条内部管线，只是输出装配策略不同。

### 5.1 场景一：AI 互动对话伴侣（Interactive Dialogue）

对应 ProcessingMode.DIALOGUE。这是标准的强输出交互场景（如心理辅导数字人、私人 AI 助理）。

- **拼接与输出逻辑**：系统必须在毫秒级时间内组装完整的 Context Package（即：回忆块 + 残影 + 最新用户输入）。大模型以此为 Prompt，向用户输出符合角色当前情感量化状态（见 §2.5.4 的 $\bar{v}, \bar{a}$）的自然语言回复。
- **后台异步代谢**：在生成回复后，系统在后台对刚才的对话过程进行残影剥离、摘要计算与基本事件的封装入库，不阻塞前台的用户对话体验。
- **模式属性**：returns_context_package = True，额外装配 npc_directives = 
  。

### 5.2 场景二：个人生活录音与被动日志提取（Passive Logging）

对应 ProcessingMode.PASSIVE_LOG。应用于如穿戴设备录音记录、长期会议监听或个人日志辅助等"只记不说"的场景。

- **拼接与输出逻辑**：该场景下不需要对输入内容提供任何外部文本输出。系统对调用方处于"静默倾听"状态，ingest 返回的 context_package 字段为 None。
- **内部仍完整回忆**：即便不对外回复，系统依然会组装回忆块、登记 recall_log、触发频繁子集挖掘。这是白皮书唯一承认的抽象合成路径，不能被模式绕过；否则长期被动记录将永远不会产生归纳事件，与 §3 定义冲突。可以把这一层理解为"对用户静默，但对自己的记忆不静默"。
- **后台执行管线**：不存在前台回复步骤。结合 2.2 节的单人模式或多人模式配置，系统接收到长音频转写的文本流后，将其直接送入残影缓冲区。达到 len_msg 阈值后自动触发切分、剔除冗余口水话、提取事实生成基本事件、更新时间线白描、在内部回忆驱动下持续产出高阶抽象事件。在此场景下，REMS 纯粹扮演一个高维度的"自治数据库"。
- **模式属性**：returns_context_package = False。

### 5.3 场景三：生成式虚拟沙盒与复杂 NPC 生态（Generative Agents）

对应 ProcessingMode.NPC_AGENT。应用于开放世界游戏或多智能体模拟环境。

- **拼接与输出逻辑**：环境事件（如"玩家进入酒馆"）作为输入，触发现场所有 NPC 的回忆检索。此时的输出不再是单纯的"对话"，而是被隐性指令转化器（Directive Parser）翻译为具体的状态机改变或寻路决策。
- **执行案例**：系统拼接 回忆块 (玩家曾在村口伤害过该 NPC) + 当前输入 (玩家靠近)，输出结果直接转化为 NPC 系统底层的行为代码（如 Action: Flee 或 Action: Attack），并同步提升该 NPC 的唤醒度并设置负效价，整个过程无需任何人类可见的文本对话生成。
- **模式属性**：returns_context_package = True，额外装配 npc_directives（动作 + 情感增量）供下游 Directive Parser 消费。
